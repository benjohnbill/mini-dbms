# mini-dbms 최종 PRD

Status: ready-for-agent

요구사항: L1~L51 (`docs/requirements.md`). 이 문서는 PRD 초안 세 개(CJG, DA, LMH)를 2026-11-16 팀 회의에서 견주어 정한 답입니다. 회의 뒤 AI에게 맡긴 세부 결정은 이슈 01~05에 있고, 이 문서는 그 결정을 따릅니다. 이 문서가 나온 뒤에는 PRD 초안을 고치지 않습니다.

## Problem Statement

앱이 데이터를 파일에 직접 쓰고 읽으면, 무엇을 찾는지와 어떻게 찾는지가 앱 코드 안에 섞입니다. 찾는 방법을 바꾸려면(예: 인덱스 추가) 앱 코드를 고쳐야 합니다. 팀은 SQL 문장 하나로 원하는 것만 말하면 DB가 찾는 방법을 스스로 정하는 작은 DBMS를 C로 직접 만들어야 합니다. 이 DBMS는 세 단계를 거칩니다. SQL 파일을 CLI로 실행해 파일에 저장하고 읽습니다(Phase 1). 100만 건 위에서 `id` 조회는 B+ 트리로, 다른 필드 조회는 전체 탐색으로 처리하고 속도 차이를 보여 줍니다(Phase 2). 외부 클라이언트가 HTTP로 같은 엔진을 여러 스레드에서 동시에 쓸 수 있습니다(Phase 3). 팀원 누구나 핵심 로직을 말로 설명할 수 있어야 합니다(L32).

## Solution

하나의 DB 엔진 라이브러리를 만들고, CLI와 HTTP 서버가 같은 엔진 함수를 부릅니다.

```text
CLI (SQL 파일) ──┐
                 ├─► 엔진: 토크나이저 → 파서 → 검증 → planner → 실행
HTTP 서버 ───────┘                                   │
 (Mongoose + 스레드 풀)                     SCAN ────┴──── INDEX
                                             │               │
                                    테이블 파일 (바이너리)   B+ 트리 (메모리)
```

- 엔진은 SQL 문장 하나를 받아 결과 구조체 하나를 돌려줍니다. 결과에는 레코드와 함께 접근 경로(`INDEX` 또는 `SCAN`)와 읽은 record 수가 들어 있습니다.
- 테이블 파일이 원본입니다. 시작할 때 파일을 끝까지 읽어 다음 ID와 B+ 트리를 만들고, 깨진 파일이면 시작을 멈춥니다.
- 서버는 HTTP 요청에서 SQL을 꺼내 작업 대기열에 넣고, 작업 스레드가 엔진을 부른 뒤 결과를 JSON으로 돌려줍니다. 테이블마다 쓰기 우선 읽기·쓰기 잠금 하나가 동시 요청을 조정합니다.

## User Stories

CLI와 SQL

1. 팀원으로서, SQL 파일 경로와 데이터 폴더를 CLI에 넘겨 파일 안의 문장을 위에서부터 차례로 실행하고 싶습니다. LMS L8의 흐름을 그대로 보이기 위해서입니다.
2. 팀원으로서, `INSERT INTO users VALUES ('kim', 'kim@example.com', 20);`처럼 `id`를 뺀 값을 스키마 순서대로 적어 record 하나를 넣고 싶습니다. 자동 ID만 쓰기 위해서입니다.
3. 팀원으로서, INSERT 성공 뒤 발급된 ID를 보고 싶습니다. 방금 넣은 record를 바로 조회하기 위해서입니다.
4. 팀원으로서, `SELECT * FROM users;`로 모든 record를 보고 싶습니다.
5. 팀원으로서, `SELECT name, age FROM users WHERE id = 3;`처럼 원하는 field만 고르고 싶습니다.
6. 팀원으로서, `WHERE field = 값` 조건 하나로 record를 거르고 싶습니다.
7. 팀원으로서, `select`와 `SELECT`를 같게 쓰고 싶습니다. 키워드는 대소문자를 구분하지 않기 때문입니다.
8. 팀원으로서, 문자열 값 안에 작은따옴표를 `''`로 적고 싶습니다(`'O''Brien'`).
9. 팀원으로서, 문자열 안의 `;`가 문장을 끊지 않기를 원합니다.
10. 팀원으로서, 문법 오류가 몇 번째 줄에서 무엇을 기대했는지 알고 싶습니다. 오류를 빨리 고치기 위해서입니다.
11. 팀원으로서, 없는 테이블, 없는 field, 값 개수 불일치, 타입 불일치를 각각 다른 오류로 받고 싶습니다.
12. 팀원으로서, `WHERE id = 'abc'`가 전체 탐색으로 넘어가지 않고 타입 오류가 되기를 원합니다.
13. 팀원으로서, SQL 파일의 첫 오류에서 실행이 멈추고, 그 앞의 성공은 남고, 뒤의 문장은 실행되지 않기를 원합니다.
14. 팀원으로서, SELECT 결과를 TSV로 stdout에서 받고 싶습니다. 기능 테스트가 출력을 그대로 비교하기 위해서입니다.
15. 팀원으로서, 접근 경로, 읽은 record 수, 걸린 시간을 stderr의 한 줄로 보고 싶습니다.
16. 팀원으로서, 100만 건을 넣을 때 `-q`로 INSERT 결과 출력을 끄고 싶습니다. 출력이 적재 속도의 병목이 되지 않게 하기 위해서입니다.
17. 팀원으로서, 종료 코드로 성공(0), 실행 오류(1), 잘못된 CLI 인자(2)를 구분하고 싶습니다.
18. 팀원으로서, 바이너리 테이블 파일을 사람이 읽는 줄로 출력하는 `dump` 명령을 쓰고 싶습니다. 에디터로는 바이너리 내용을 볼 수 없기 때문입니다.

저장과 복구

19. 팀원으로서, 프로그램을 다시 실행해도 저장한 record를 조회하고, ID가 이어지기를 원합니다.
20. 팀원으로서, 테이블마다 스키마 파일 하나를 미리 만들고 `id`는 적지 않기를 원합니다. `CREATE TABLE`이 필요 없게 하기 위해서입니다(L19).
21. 팀원으로서, 테이블 파일이 깨져 있으면 엔진이 시작을 멈추고 파일 이름과 바이트 위치를 알려 주기를 원합니다. 깨진 데이터를 정상으로 읽지 않기 위해서입니다.
22. 팀원으로서, 엔진이 깨진 파일을 스스로 고치지 않기를 원합니다. 사람이 원인을 보고 고치기 위해서입니다.
23. 팀원으로서, INSERT가 파일 쓰기에 실패하면 파일이 쓰기 전과 같아지고 ID가 소비되지 않기를 원합니다.
24. 팀원으로서, 되돌리기까지 실패하면 그 테이블만 멈추고 다른 테이블은 계속 쓸 수 있기를 원합니다.
25. 팀원으로서, 같은 데이터 폴더를 두 프로세스가 동시에 쓰지 못하기를 원합니다. 같은 ID가 두 번 나가지 않게 하기 위해서입니다.
26. 팀원으로서, 같은 테이블 파일을 mac과 linux에서 똑같이 읽기를 원합니다.

B+ 트리와 측정

27. 팀원으로서, `WHERE id = k`가 B+ 트리로 record 하나만 읽기를 원합니다(L39).
28. 팀원으로서, 다른 field 조건은 전체 탐색을 하기를 원합니다(L25).
29. 팀원으로서, 없는 ID를 찾으면 접근 경로는 `INDEX`, 결과 0건, 읽은 record 수 0을 받기를 원합니다.
30. 팀원으로서, 시드를 고정한 생성 스크립트로 100만 건 SQL 파일을 매번 같게 만들고 싶습니다(L40).
31. 팀원으로서, 생성한 SQL 파일을 Phase 1의 CLI로 그대로 넣고 싶습니다(L26).
32. 팀원으로서, 같은 엔진 세션에서 INDEX와 SCAN 조회를 반복해 중앙값과 p99를 재고 싶습니다. 시작 시간과 터미널 출력이 측정에 섞이지 않게 하기 위해서입니다.
33. 팀원으로서, 레코드 위치(앞, 중간, 뒤), 없는 값, 같은 ID를 강제로 SCAN한 경우까지 재고 싶습니다. SCAN 시간이 위치에 따라 어떻게 달라지는지 보이기 위해서입니다.
34. 팀원으로서, 측정 결과를 트리 높이, 메모리, 환경과 함께 측정 기록으로 남기고 싶습니다.
35. 팀원으로서, B+ 트리 노드 크기를 감이 아니라 측정으로 고르고 싶습니다.

HTTP API와 동시성

36. 클라이언트 개발자로서, `POST /query`의 본문에 SQL 문장 하나를 그대로 넣어 실행하고 싶습니다. `curl --data-binary`로 바로 부르기 위해서입니다.
37. 클라이언트 개발자로서, SELECT 결과를 `fields`, `records`, `access_path`, `records_examined`가 담긴 JSON 하나로 받고 싶습니다.
38. 클라이언트 개발자로서, INSERT 성공 응답에서 발급된 `id`를 받고 싶습니다.
39. 클라이언트 개발자로서, 실패 이유를 HTTP 상태 코드와 기계가 읽는 오류 이유(`syntax_error`, `queue_full` 등)로 구분하고 싶습니다.
40. 클라이언트 개발자로서, 문장이 둘 이상인 요청은 어느 문장도 실행되지 않고 거절되기를 원합니다.
41. 클라이언트 개발자로서, 결과가 1만 건을 넘으면 `next_cursor`를 받아 이어서 요청하고 싶습니다.
42. 클라이언트 개발자로서, 한 연결로 여러 요청을 차례로 보내고 싶습니다(HTTP/1.1 keep-alive).
43. 클라이언트 개발자로서, 서버가 바쁘면 기다리지 않고 바로 `503`을 받고 싶습니다.
44. 클라이언트 개발자로서, 응답을 받기 전에 연결이 끊겨도 서버가 받은 INSERT는 저장되기를 원합니다.
45. 운영하는 팀원으로서, 여러 SELECT가 동시에 실행되고 INSERT만 하나씩 실행되기를 원합니다.
46. 운영하는 팀원으로서, SELECT가 계속 들어와도 INSERT가 끝없이 기다리지 않기를 원합니다(쓰기 우선).
47. 운영하는 팀원으로서, 동시 INSERT 100개가 각자 다른 ID를 받고 데이터가 서로 바뀌지 않기를 원합니다.
48. 운영하는 팀원으로서, 응답을 천천히 읽는 클라이언트가 잠금이나 작업 스레드를 붙잡지 않기를 원합니다.
49. 운영하는 팀원으로서, SIGINT를 보내면 받은 요청을 끝까지 처리한 뒤 정해진 순서로 종료하기를 원합니다.
50. 운영하는 팀원으로서, 서버가 기본으로 로컬 접속만 받고, 시연 때만 옵션으로 열기를 원합니다.
51. 운영하는 팀원으로서, 스레드 수와 대기열 길이를 실행 인자로 바꾸고 싶습니다.
52. 발표하는 팀원으로서, 엔진이 고른 경로(INDEX 또는 SCAN)를 결과에서 바로 보여 주고 싶습니다. "어떻게"를 엔진이 정한다는 점을 보이기 위해서입니다.

## Implementation Decisions

### 공통

- **범위**: LMS 기본선(Phase 1~3)을 팀 범위로 합니다. "실제로 쓰는 DBMS" 목표는 차별점 후보로 둡니다.
- **언어와 빌드**: C11, Makefile. 검증 명령은 `make verify`(경고를 오류로 보는 빌드, ASan·UBSan 단위 테스트, 기능 테스트)이고 CI도 같은 명령을 씁니다. Phase 2에 `make bench`, Phase 3에 `make tsan`을 더합니다. 지원 OS는 macOS와 Linux(WSL 2 포함)이고, 두 OS에서 같은 테스트가 같은 결과를 내야 합니다. 그래서 glibc 전용 기능은 쓰지 않습니다.
- **용어**: 코드와 문서에서 record, field를 씁니다(테이블의 행과 열). `GLOSSARY.md`에 올립니다.
- **엔진 인터페이스**: 함수 네 개(엔진 만들기, 문장 하나 실행, 결과 해제, 엔진 해제)입니다. 실행 함수는 한 번에 문장 하나만 실행합니다. CLI 모드에서는 파서가 다음 문장의 시작 위치를 돌려주고, CLI가 그 위치부터 다시 부릅니다. 그래서 문자열 안의 `;`에서 문장이 잘리지 않습니다. API 모드에서는 문장 뒤에 다른 문장이 있으면 실행 전에 거절합니다. 엔진 옵션으로 결과 상한(record 수, 누적 바이트)을 받으며, CLI는 상한을 두지 않습니다.
- **결과 전달**: 엔진은 결과를 구조체에 모두 모아 돌려줍니다. 엔진 안의 record 읽기는 iterator(다음 record, 닫기) 모양이라 실행기는 SCAN인지 INDEX인지 모릅니다. 잠금은 실행 단계에서만 쥐고, JSON 만들기와 전송은 잠금 밖에서 합니다.
- **큰 결과 나눠 받기**: HTTP SELECT 결과가 1만 건을 넘으면 처음 1만 건과 `next_cursor`(다음 record의 바이트 위치)를 돌려주고, 클라이언트는 같은 SQL을 커서와 함께 다시 보냅니다. 세부와 검증할 주장은 이슈 05에 있습니다. 기본선의 다른 기능 뒤에 구현합니다.
- **데이터 폴더 독점**: 엔진을 만들 때 데이터 폴더의 잠금 파일에 비차단 배타 `flock`을 겁니다. 이미 잠겨 있으면 시작이 실패합니다.
- **영속성**: `fsync`를 하지 않습니다. 정전 때 성공을 알린 record를 잃을 수 있고, 이 점을 "알려진 한계"에 적습니다.
- **깨진 파일**: 시작할 때 테이블 파일을 끝까지 읽어 `잘림`이나 `손상`을 찾으면 시작을 멈추고 파일 이름, 바이트 위치, record 번호를 알립니다. 파일은 고치지 않습니다. 기본선에는 CRC가 없습니다. 판정 규칙은 이슈 01에 있습니다.
- **INSERT 실패**: 쓰기 전에 메모리 할당을 모두 끝내고, 쓰기가 실패하면 파일을 쓰기 전 길이로 되돌립니다. 되돌리기도 실패하면 그 테이블을 멈춥니다. 실패한 INSERT는 ID를 소비하지 않습니다. 순서와 응답 표는 이슈 02에 있습니다.

### Phase 1 · SQL 처리기

- **파서**: 직접 쓴 토크나이저와 재귀 하강 파서입니다. 토큰마다 줄과 칸 위치를 담아, 문법 오류에 줄 번호와 기대한 토큰을 적습니다. 파서는 문장 종류, 테이블, field 목록, 값 목록, WHERE 조건을 문장 구조체에 담고, 실행기는 SQL 문자열을 다시 보지 않습니다.
- **어휘 규칙**: 키워드는 대소문자를 구분하지 않고, 테이블과 field 이름은 구분합니다. 문자열은 작은따옴표로 감싸고 안의 작은따옴표는 `''`로 적습니다. 모든 문장은 `;`로 끝납니다. 주석은 지원하지 않습니다.
- **INSERT**: `INSERT INTO 테이블 VALUES (값, …);` 한 행입니다. field 목록은 적지 않고, `id`를 뺀 모든 field의 값을 스키마 순서대로 적습니다. `id`를 적으면 오류입니다.
- **SELECT**: `SELECT (* 또는 field 목록) FROM 테이블 [WHERE field = 값];`입니다. WHERE는 field 하나와 `=` 하나입니다. 결과 순서는 보장하지 않습니다.
- **실행 순서**: 검증 → planner → 실행입니다. 검증은 테이블과 field가 있는지, 값 개수와 타입이 스키마와 맞는지 먼저 확인하고, 통과한 SELECT에만 planner가 접근 경로를 고릅니다.
- **타입**: `INT`는 64비트 부호 있는 정수이고 범위를 넘으면 오류입니다. `TEXT` 값 하나는 최대 1 MiB입니다. `NULL`은 없습니다.
- **자동 ID**: 테이블마다 1부터 1씩 올립니다. 재시작하면 가장 큰 ID 다음부터 냅니다. 실패한 INSERT는 ID를 소비하지 않습니다. ID가 `INT` 최댓값에 닿으면 새 INSERT는 오류입니다.
- **테이블 파일**: 테이블마다 파일 하나에 record를 덧붙이기만 합니다. record는 본문 길이(4바이트)와 본문입니다. 본문은 `id`(8바이트)와 스키마 순서의 field 값이고, `INT`는 8바이트, `TEXT`는 길이(4바이트)와 UTF-8 바이트입니다. 모든 정수는 리틀 엔디언입니다. 이 레이아웃은 이슈 01에서 정했습니다.
- **스키마 파일**: 테이블마다 스키마 파일 하나를 사람이 미리 만듭니다. 한 줄에 field 하나(`name TEXT`)를 적고, `id`는 적지 않습니다. 테이블 이름은 파일 이름입니다.
- **잘못된 테이블**: 스키마 오류, 데이터 파일 없음, 깨진 테이블 파일 중 하나라도 있으면 엔진 시작을 멈춥니다. 엔진은 "모든 테이블이 정상"이라는 가정 하나로 동작합니다.
- **CLI**: 인자는 `[--data 폴더] [-q] <SQL 파일>`입니다. SQL 파일 전체를 메모리에 읽고, NUL 바이트가 있으면 입력 오류입니다. SELECT 결과는 stdout에 TSV(첫 줄은 field 이름)로, 메타 정보는 stderr에 한 줄로 씁니다. 종료 코드는 0(성공), 1(파일·SQL·실행 오류), 2(잘못된 인자)입니다. `dump` 명령은 테이블 파일을 TSV 줄로 출력합니다.

### Phase 2 · B+ 트리

- **모듈**: 테이블을 모르는 일반 모듈로, `int64` 키(record `id`)를 `uint64` 값(테이블 파일 안의 record 시작 위치)에 연결합니다. 메모리에만 둡니다(L21). 리프끼리 연결하고, 삭제와 중복 키는 없습니다. 삽입에 필요한 노드를 미리 할당하는 함수를 두어, 파일을 쓴 뒤의 삽입이 실패하지 않게 합니다. 근거는 이슈 03에 있습니다.
- **노드 크기**: 상수로 두고, 16, 32, 64, 128을 측정해 고릅니다(이슈 03). 분할은 반씩 나눕니다.
- **재구성**: 엔진을 만들 때 테이블 파일을 읽으면서 다음 ID와 B+ 트리를 같이 만듭니다. 인덱스 파일은 없습니다.
- **planner**: `WHERE id = 정수`이면 INDEX, 그 밖은 SCAN입니다. INDEX는 트리에서 위치를 찾아 그 record 하나만 `pread`로 읽습니다. INDEX로 찾은 record를 조건과 다시 비교하지는 않고, 정확성은 B+ 트리 단위 테스트가 보증합니다.
- **결과 메타**: 모든 SELECT 결과에 접근 경로와 읽은 record 수를 담습니다. CLI는 stderr에, HTTP는 JSON에 보여 줍니다.
- **데이터 생성**: 생성 스크립트가 시드와 행 수를 받아 INSERT 문이 든 SQL 파일을 만듭니다. 비교에 쓰는 field 값은 행마다 다르게 만들어, `id` 조회와 다른 field 조회가 같은 record 1건을 돌려주게 합니다.
- **측정**: 엔진을 직접 링크한 측정 프로그램(`-O2`, sanitizer 끔)으로, 엔진 준비가 끝난 뒤부터 잽니다. 두 경로를 한 번씩 데운 뒤 INDEX는 1,000번(중앙값, p99), SCAN은 30번(중앙값, 최소, 최대) 잽니다. 질의 세트는 위치별(앞, 중간, 뒤), 없는 값, 같은 ID를 강제로 SCAN한 경우를 포함합니다. 강제 SCAN 경로는 측정 전용이고 일반 SQL의 planner 규칙을 바꾸지 않습니다. 측정 시나리오는 앞으로 더 늘어납니다.

### Phase 3 · API 서버

- **HTTP**: Mongoose 7.23의 이벤트 루프 위에 스레드 풀과 작업 대기열을 직접 만듭니다(L29). Mongoose는 GPLv2라 mini-redis처럼 저장소 루트에 GPLv2 LICENSE를 둡니다. 작업 스레드는 결과를 완료 대기열에 넣고 이벤트 루프를 깨우기만 하며, 응답은 이벤트 루프만 보냅니다.
- **스레드 풀**: 기본 스레드 8개, 대기열 128칸이고 실행 인자로 바꿉니다. 대기열이 가득 차면 기다리지 않고 `503 queue_full`로 답합니다.
- **연결**: HTTP/1.1 keep-alive를 씁니다. 같은 연결의 다음 요청은 앞 응답을 송신 버퍼에 넣은 뒤 처리합니다. `Connection: close` 요청과 keep-alive가 없는 HTTP/1.0 요청에는 응답 뒤 연결을 닫습니다.
- **요청**: `POST /query`, 본문은 SQL 문장 하나이고 `Content-Length`가 필수입니다. 본문 상한은 1 MiB, 헤더 상한은 8 KiB이며 Mongoose 수신 버퍼 한도보다 작게 둡니다. NUL 바이트가 든 본문은 거절합니다.
- **응답**: SELECT 성공은 `200`과 `{fields, records, access_path, records_examined}`, INSERT 성공은 `200`과 `{inserted, id}`입니다. 1만 건을 넘으면 `next_cursor`가 붙습니다. 오류는 `{error, message}`입니다. 정수는 JSON 숫자로 보냅니다.
- **상태 코드**: DA 초안의 표를 따릅니다. `400`(본문 길이, SQL 오류, 빈 본문, 여러 문장, `invalid_cursor`), `404`(다른 경로), `405`(POST가 아님, `Allow: POST`), `411`(chunked), `413`(본문 상한 초과), `503`(`queue_full`, `shutting_down`), `500`(`storage_error`, `table_unavailable`, `out_of_memory`).
- **동시성**: 테이블마다 쓰기 우선 읽기·쓰기 잠금 하나를 둡니다. 이 잠금은 mutex와 조건 변수 두 개로 직접 구현해 mac과 linux에서 같게 동작합니다. 여러 SELECT는 동시에 읽고, INSERT는 하나씩 쓰며, INSERT가 기다리기 시작하면 새 SELECT는 기다립니다. ID 발급, 파일 쓰기, B+ 트리 등록, 실패 시 되돌리기는 모두 같은 쓰기 잠금 안에서 합니다. 엔진 안에서 잠금을 다시 잡는 경로는 두지 않습니다. 테이블 목록은 시작 뒤 바뀌지 않습니다.
- **읽기 위치**: record는 `pread`로 읽어, 읽기 잠금을 같이 쥔 스레드끼리 파일 위치를 바꾸지 않습니다.
- **느린 클라이언트**: 이벤트 루프가 비차단으로 보내므로 작업 스레드와 잠금은 붙잡히지 않습니다. 일정 시간 동안 주고받는 데이터가 없는 연결은 이벤트 루프의 타이머가 닫습니다. 시간 값은 구현할 때 정하고 설정할 수 있게 합니다.
- **종료**: SIGINT를 받으면 새 연결을 받지 않고, 받은 작업을 끝까지 처리하고, 남은 응답 전송을 최대 5초 기다린 뒤 작업 스레드, Mongoose 매니저, 엔진 순서로 정리합니다. 세부는 이슈 04에 있습니다.
- **접속 범위**: 기본은 127.0.0.1입니다. 시연 때 옵션으로 다른 주소를 엽니다.
- **끊긴 연결**: 서버가 대기열에 넣은 INSERT는 연결이 끊겨도 끝까지 처리합니다. 응답을 받지 못한 클라이언트가 다시 보내면 record가 중복될 수 있습니다.

### 차별점 순서

1. 재현 가능한 측정 도구와 성능 그래프
2. `EXPLAIN` (실행하지 않고 고른 경로만 출력)
3. 두 번째 인덱스 (`id`가 아닌 field의 B+ 트리)

그 뒤 후보: 큰 결과 커서(이슈 05, 기본선 기능 뒤), 자동 복구와 CRC, 저널과 여러 행 INSERT, INSERT field 목록, 스냅샷 읽기, REPL, 오른쪽 끝 분할.

## Testing Decisions

- **좋은 테스트**: 공개 함수를 불러 겉으로 보이는 동작만 확인합니다. 기대값은 검사 대상 함수로 계산하지 않고 직접 적습니다. 테스트 이름은 동작을 말하는 한국어 문장이고, 엣지 케이스 목록은 테스트 이름이 맡습니다(`CONVENTION.md` § 테스트).
- **가장 높은 틈: 엔진 인터페이스**. SQL 처리, 저장, 재시작, 인덱스 경로, 깨진 파일, INSERT 실패를 엔진의 네 함수와 임시 데이터 폴더로 확인합니다. CLI와 서버는 이 틈 위의 얇은 층입니다.
- **프로세스 틈: CLI와 서버**. Python 기능 테스트가 CLI 실행 파일에 SQL 파일을 넘겨 stdout, stderr, 종료 코드를 비교하고(L47), 실제 서버에 HTTP 요청을 보내 상태 코드와 JSON을 비교합니다(L49).
- **모듈 틈: B+ 트리, 쓰기 우선 잠금, 작업 대기열**. 세 모듈은 엔진 없이 단위 테스트합니다. B+ 트리는 100만 키, 분할 경계, 테스트 전용 불변식 검사(리프 깊이, 키 순서, 키 수)로 확인합니다. 잠금은 읽기 동시 진입, 쓰기 배타, 쓰기 대기 중 새 읽기 차단을 확인합니다. 대기열은 시간에 기대지 않도록 테스트가 쥔 조건 변수로 첫 작업을 멈춰 두고 가득 참을 확인합니다.
- **파일 함수 틈**: 쓰기 실패와 되돌리기 실패를 만들기 위해, 테이블 코드는 파일 쓰기와 자르기를 함수 포인터 표로 부르고 테스트가 그 표를 바꿉니다(이슈 02). 새로 만드는 틈은 이것 하나입니다.
- **인덱스 경로 확인(L48)**: 있는 ID는 `INDEX`·1건, 없는 ID는 `INDEX`·0건, 다른 field는 `SCAN`·전체 record 수, 타입이 틀린 조건은 오류입니다.
- **동시성(L42, L49)**: 동시 INSERT 100개가 ID 1~100을 받고, 각 INSERT에 넣은 고유 표식이 그 ID로 다시 조회되는지 확인합니다. SCAN과 INSERT를 섞어 반쯤 쓰인 record가 보이지 않는지 확인합니다. 동시성 테스트는 `make tsan`에서도 돌립니다.
- **시나리오 목록**: 도구와 판정 기준은 DA 초안 8절을, 시나리오는 LMH 초안의 "주요 검증 시나리오"를 따릅니다.
- **선례**: mini-redis의 acutest 단위 테스트, Python 기능 테스트, `make verify`와 CI 구성을 그대로 가져옵니다.

## Out of Scope

- `UPDATE`, `DELETE`, `CREATE TABLE`(L19), `JOIN`, `ORDER BY`, 집계 함수, `AND`·`OR`·범위 비교, `LIMIT`, `NULL`
- SQL 주석, INSERT field 목록, 여러 행 INSERT
- 트랜잭션, `fsync`, 비정상 종료나 전원 장애 뒤의 자동 복구, CRC
- 디스크 기반 B+ 트리(L21), 인덱스 파일
- 사용자 인증과 권한, 다른 컴퓨터에서의 접속(옵션으로만 엶)
- 서버 전체 메모리 상한(요청, 결과, 대기열에만 상한이 있음)
- Windows 네이티브 실행
