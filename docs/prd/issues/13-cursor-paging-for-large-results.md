# 13: 1만 건이 넘는 SELECT 결과를 커서로 나눠 받기

**What to build:** HTTP SELECT 결과가 1만 건을 넘으면, 서버가 `400 result_too_large`(티켓 11) 대신 처음 1만 건과 `next_cursor`를 돌려주고, 클라이언트는 같은 SQL을 커서와 함께 다시 보내 다음 부분을 받습니다. 회의(2026-11-16)에서 결과 전달은 "결과를 모아 JSON 하나로 보냄"으로 정했고, 1만 건이 넘으면 잘라서 받기로 했습니다. 한 응답에 조각을 이어 보내는 방식은 LMH 초안의 순차 전송과 같은 구조라서 전송이 끝날 때까지 읽기 잠금을 쥡니다. 그래서 고르지 않았습니다. 팀은 이 설계를 구현할 때 검증할 영역으로 정했고, 아래 "검증할 주장"이 그 대상입니다. 기본선(티켓 01\~12) 뒤, 차별점 앞에 합니다.

**Blocked by:** 11

**Status:** done

## API

- SELECT 응답에 `"next_cursor": <정수>`가 붙을 수 있습니다. 정수는 SCAN이 아직 읽지 않은 다음 record의 바이트 위치입니다.
- 클라이언트는 같은 SQL을 `POST /query?cursor=<정수>`로 다시 보냅니다. 본문은 그대로 SQL입니다.
- SCAN이 `committed_size`에 닿으면 응답에 `next_cursor`가 없습니다.
- 한 번에 보내는 양은 1만 건 또는 결과 바이트 상한 중 먼저 닿는 쪽까지입니다.
- `result_too_large`는 record 하나가 바이트 상한보다 클 때만 남습니다.
- CLI는 나눠 받지 않습니다. CLI에는 결과 상한이 없습니다.

## 엔진

서버용으로 커서 위치에서 시작하는 실행 함수를 하나 더합니다. CLI가 쓰는 실행 함수는 그대로입니다. SCAN은 커서에서 시작해 상한에서 멈추고, 읽기 잠금은 그 부분을 읽는 동안만 쥡니다.

## 커서 검사

커서는 record가 시작하는 위치여야 합니다. 그 위치의 record를 읽고, 그 `id`를 B+ 트리에서 찾아 트리가 같은 위치를 돌려주면 올바른 커서입니다. 아래 경우는 새 오류 이유 `400 invalid_cursor`입니다.

- record 시작이 아닌 위치
- `committed_size`보다 큰 위치
- 0 이상의 정수가 아닌 값
- INDEX 경로를 쓰는 질의에 붙은 커서. INDEX 질의는 결과가 많아야 1건이라 나눌 일이 없습니다.

## 검증할 주장

이 설계는 한 가지 성질에 기댑니다. 테이블 파일은 덧붙이기만 하고, 기본선에는 UPDATE와 DELETE가 없습니다.

1. 부분 사이에 INSERT가 없으면, 부분들을 이은 결과가 SCAN 한 번의 결과와 같습니다.
2. 부분 사이에 INSERT가 있으면, 새 record는 조건에 맞을 때 뒤 부분에만 나옵니다. 앞서 받은 record가 다시 나오거나 빠지지 않습니다.
3. 부분 하나를 읽는 동안만 읽기 잠금을 쥡니다.
4. 1만 건 한 부분의 메모리와 응답 시간을 재서 상한 1만이 적당한지 정합니다. 결과는 측정 기록으로 남깁니다.

부분들은 한 시점의 스냅샷이 아닙니다. `README.md`의 "알려진 한계"에 적습니다. UPDATE나 DELETE를 범위에 넣으면 이 설계를 다시 검토합니다.
