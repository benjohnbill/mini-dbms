# 06: B+ 트리 일반 모듈

**What to build:** 테이블을 모르는 B+ 트리 모듈을 만들고, 엔진 없이 단위 테스트로 정확성을 보입니다. 모듈은 `int64` 키를 `uint64` 값에 연결합니다. 엔진에서 키는 record의 `id`이고, 값은 테이블 파일 안에서 그 record가 시작하는 바이트 위치입니다. 엔진 연결은 티켓 07이, 노드 크기 측정은 티켓 08이 합니다. 이 티켓은 한 층만 만들지만, `docs/prd/final.md`의 Testing Decisions가 이 모듈을 엔진 없이 테스트하는 대상으로 정했기 때문에 따로 둡니다.

**Blocked by:** 01

**Status:** ready-for-agent

## 모듈 경계

함수는 다섯 개입니다. 트리 만들기, 삽입 한 번에 필요한 노드를 미리 할당하기, 삽입, 찾기, 트리 해제입니다. 미리 할당이 성공한 뒤의 삽입은 메모리를 할당하지 않고 실패하지 않습니다. 파일을 쓴 뒤의 트리 삽입이 실패하면 안 되기 때문입니다(티켓 07). 리프끼리 다음 리프를 가리킵니다. 삭제와 중복 키는 없습니다. 노드 크기는 상수이고, 티켓 08이 측정으로 고르기 전에는 32로 둡니다. 분할은 반씩 나눕니다.

## 왜 일반 모듈인가

| 선택 | 결과 |
|---|---|
| **`int64 → uint64` 일반 모듈 (선택)** | 테이블 파일 없이 단위 테스트를 돌립니다. 키 100만 개를 넣고 디스크 입출력 없이 트리를 검사합니다. 엔진과의 경계가 함수 다섯 개뿐이고, 테이블에 대한 지식은 planner와 실행기만 가집니다. |
| record 전체를 트리에 저장 (클러스터 인덱스) | 트리가 저장소가 됩니다. 테이블 파일이 원본이 아니게 되어 파일 기반 저장(L36)과 시작할 때 재구성 결정과 맞지 않습니다. record 100만 건이 모두 메모리에 남습니다. |
| 테이블을 아는 트리 (record에서 키를 직접 꺼냄) | 트리 테스트마다 파일 형식과 스키마가 필요합니다. 파일 형식을 바꾸면 트리도 바뀝니다. |
| 비교 함수와 `void *` 키를 받는 일반 트리 | 두 번째 인덱스(차별점 3, 키가 `(값, id)`)에만 필요합니다. 비교마다 간접 호출이 늘어납니다. 두 번째 인덱스를 시작할 때 바꿉니다. |

완료 조건:

- [ ] 오름차순 키 100만 개를 넣은 뒤 모든 키가 제 값과 함께 찾아집니다.
- [ ] 넣지 않은 키는 찾아지지 않습니다.
- [ ] 분할 경계(노드 크기 N개와 N+1개)에서 모든 키가 찾아집니다.
- [ ] 루트가 분할된 뒤에도 기존 키와 값이 유지됩니다.
- [ ] 테스트 전용 검사로 모든 리프의 깊이가 같고, 리프 연결을 따라 키가 오름차순이며, 키 수가 삽입 수와 같은지 확인합니다.
- [ ] 미리 할당이 성공한 뒤의 삽입은 메모리를 할당하지 않습니다. 테스트는 할당 함수를 세는 방식으로 확인합니다.
