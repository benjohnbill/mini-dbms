# 03: B+ 트리를 일반 모듈로 만들고 노드 크기는 측정으로 정하기

**Status:** ready-for-agent

**What to build:** 테이블을 모르는 B+ 트리 모듈을 만들고, 노드 크기를 측정으로 고릅니다. 회의(2026-11-16)에서 DA 설계(`docs/prd/DA.md` 6.1)를 골랐고, 왜 그 설계가 최선인지를 이 티켓에 남기기로 했습니다.

**Blocked by:** None (can start immediately)

## 모듈 경계

모듈은 `int64` 키를 `uint64` 값에 연결합니다. 엔진에서 키는 레코드의 `id`이고, 값은 테이블 파일 안에서 그 레코드가 시작하는 바이트 위치입니다.

```c
struct bptree *bptree_create(void);
bool bptree_reserve(struct bptree *tree);   /* 삽입 한 번에 필요한 노드를 미리 할당 */
void bptree_insert(struct bptree *tree, int64_t key, uint64_t value);
bool bptree_find(const struct bptree *tree, int64_t key, uint64_t *value);
void bptree_destroy(struct bptree *tree);
```

함수 이름은 예시이고, 모양이 결정입니다. `bptree_reserve`는 파일을 쓴 뒤에는 실패하지 않는 삽입이 필요해서 둡니다(티켓 02).

## 왜 일반 모듈이 최선인가

| 선택 | 결과 |
|---|---|
| **`int64 → uint64` 일반 모듈 (선택)** | 테이블 파일 없이 단위 테스트를 돌립니다. 키 100만 개를 넣고 디스크 입출력 없이 트리를 검사합니다. 엔진과의 경계가 함수 다섯 개뿐이고, 테이블에 대한 지식은 planner와 실행기만 가집니다. |
| 레코드 전체를 트리에 저장 (클러스터 인덱스) | 트리가 저장소가 됩니다. 그러면 테이블 파일이 원본이 아니게 되어, 파일 기반 저장(L36)과 시작할 때 재구성 결정과 맞지 않습니다. 레코드 100만 건이 모두 메모리에 남습니다. |
| 테이블을 아는 트리 (레코드에서 키를 직접 꺼냄) | 트리 테스트마다 파일 형식과 스키마가 필요합니다. 파일 형식을 바꾸면 트리도 바뀝니다. |
| 비교 함수와 `void *` 키를 받는 일반 트리 | 두 번째 인덱스(차별점 3, 키가 `(값, id)`, `docs/prd/CJG.md` 125줄)에만 필요합니다. 비교마다 간접 호출이 늘어납니다. 두 번째 인덱스를 시작할 때 바꾸고, 그 전에는 바꾸지 않습니다. |

## 노드 크기 측정

CJG 초안은 노드당 키 64개, DA 초안은 32개입니다. 데이터로 고릅니다.

1. 실제 INSERT 경로처럼 ID 1부터 1,000,000까지 오름차순으로 넣습니다.
2. 노드 크기 16, 32, 64, 128마다 반복합니다.
3. 트리 높이, 노드 수, 메모리 사용량, 전체 삽입 시간, 무작위 키 1,000번 `bptree_find`의 중앙값과 p99를 적습니다.
4. 결과는 `CONVENTION.md` § 측정 기록에 따라 `docs/measurements/`에 파일 하나로 남깁니다.

분할은 반씩 나눕니다. 오름차순 키에서는 왼쪽 리프가 절반 정도만 찬 채로 남습니다(`docs/prd/DA.md` 264줄). 측정에서 메모리 비용이 드러나고, 문제가 되면 오른쪽 끝 분할을 두 번째 단계로 시험합니다.

## 테스트로 확인할 것

- 오름차순 키 100만 개를 넣은 뒤 모든 키가 제 값과 함께 찾아집니다.
- 넣지 않은 키는 찾아지지 않습니다.
- 분할 경계(노드 크기 N개와 N+1개)에서 모든 키가 찾아집니다.
- 테스트 전용 검사로 모든 리프의 깊이가 같고, 리프 연결을 따라 키가 오름차순이며, 키 수가 삽입 수와 같은지 확인합니다.
- `bptree_reserve`가 성공한 뒤의 `bptree_insert`는 메모리를 할당하지 않습니다.
