# 11: 요청 방어와 keep-alive

**What to build:** 잘못되었거나 너무 크거나 끝나지 않는 요청이 서버를 멈추지 못합니다. 서버가 바쁘면 클라이언트는 기다리지 않고 바로 `503`을 받습니다. 결과가 1만 건을 넘으면 `400 result_too_large`로 거절합니다(티켓 13이 이 거절을 커서로 바꿉니다). 클라이언트는 한 연결로 여러 요청을 차례로 보낼 수 있습니다. 결정은 `docs/prd/final.md` Phase 3 절의 연결, 요청, 상태 코드, 느린 클라이언트, 끊긴 연결과 공통 절의 결과 상한을 따르고, 상태 코드 표는 DA 초안 7.3, 7.4절을 옮긴 아래 표를 따릅니다.

**Blocked by:** 10

**Status:** done

작업에 포함되는 것:

- **본문 길이**: `Content-Length`가 필요합니다. 헤더 단계에서 유효한 `Content-Length`를 먼저 확인하고, 본문을 다 받은 뒤에도 확인합니다. 선언한 길이만큼 본문을 받지 못하고 끊긴 요청은 실행하지 않습니다. `Content-Length`와 `Transfer-Encoding`이 함께 오거나 길이 표기가 틀리면 거절합니다.
- **상한**: 본문 1 MiB, 헤더 8 KiB입니다. 둘 다 Mongoose 수신 버퍼 한도보다 작게 둡니다. 라이브러리 한도에 먼저 걸리면 응답 없이 연결이 닫힐 수 있기 때문입니다.
- **결과 상한**: 엔진 옵션으로 결과 상한(record 1만 건, 누적 바이트)을 받습니다. 서버는 설정값을 넘기고, CLI는 상한을 두지 않습니다(0). 넘으면 엔진은 모으기를 멈추고 모은 record를 해제한 뒤 `result_too_large`를 돌려줍니다. 서버는 JSON을 만들면서 응답 바이트도 확인합니다.
- **대기열**: 가득 차면 `503 queue_full`로 바로 답합니다. 가득 참은 시간에 기대지 않고 테스트합니다. C 단위 테스트에서 대기열 모듈을 작업 스레드 1개, 대기열 1칸으로 만들고, 테스트가 쥔 조건 변수로 첫 작업을 멈춰 둔 채 둘째 작업이 들어간 것을 확인하고 셋째 작업이 거절되는지 봅니다. 그 다음 "가득 참 → `503`" 변환을 서버 쪽에서 따로 확인합니다.
- **keep-alive**: HTTP/1.1 연결을 재사용합니다. 같은 연결의 다음 요청은 앞 응답을 송신 버퍼에 넣은 뒤 처리합니다. 여러 연결의 요청은 병렬로 처리합니다. `Connection: close` 요청, keep-alive를 요청하지 않은 HTTP/1.0 요청, 서버가 닫기로 한 연결은 응답에 `Connection: close`를 넣고, 보낸 뒤 닫으며, 그 연결의 뒤 SQL은 받지 않습니다. 닫을지는 요청을 받을 때 기록해 두었다가 응답할 때 씁니다.
- **느린 클라이언트**: 이벤트 루프가 비차단으로 보내므로 작업 스레드와 잠금은 붙잡히지 않습니다. 일정 시간 동안 주고받은 데이터가 없는 연결은 이벤트 루프의 타이머가 닫습니다. 시간 값은 실행 인자로 바꿉니다.
- **끊긴 연결**: 대기열에 들어간 INSERT는 연결이 끊겨도 끝까지 처리합니다. 응답을 받지 못한 클라이언트가 다시 보내면 record가 중복될 수 있다는 점을 `README.md` API 절에 적습니다.
- **문서**: `docs/requirements.md`의 L50 행에 이 티켓의 테스트 이름을 근거로 더합니다.

## 이 티켓이 맡는 상태 코드 (DA 초안 7.3, 7.4절에서 옮김)

| 상태 | 오류 이유 | 언제 |
|---|---|---|
| `400` | `invalid_body_length` | 잘못된 본문 길이 헤더, `Content-Length`와 `Transfer-Encoding`이 함께 옴 |
| `400` | `invalid_sql_body` | NUL 바이트(`0x00`)가 든 본문 |
| `400` | `no_statement` | 빈 본문, 또는 공백만 있는 본문 |
| `400` | `result_too_large` | 결과가 record 1만 건 또는 바이트 상한을 넘음 |
| `411` | `length_required` | `Content-Length` 없이 chunked로 보낸 요청 |
| `413` | `body_too_large` | 헤더를 정상으로 읽었고 선언한 본문 길이가 1 MiB를 넘음 |
| `503` | `queue_full` | 작업 대기열이 가득 참 |

완료 조건:

- [ ] 표의 경우마다 상태 코드와 오류 이유가 맞고, 어떤 경우도 SQL을 실행하지 않습니다.
- [ ] 8 KiB를 넘는 헤더는 응답을 받거나 연결이 닫히며, 서버는 계속 다른 요청을 처리합니다.
- [ ] 선언한 길이보다 본문을 덜 보내고 끊은 요청은 실행되지 않습니다.
- [ ] 1만 1건을 돌려줄 SELECT는 `400 result_too_large`이고, CLI로 같은 SELECT를 실행하면 모두 나옵니다.
- [ ] 대기열 가득 참 단위 테스트와 서버 쪽 `503` 변환 테스트가 통과합니다.
- [ ] 한 연결에 요청 세 개를 연달아 보내면 보낸 순서대로 응답을 받습니다.
- [ ] 첫 요청에 `Connection: close`가 있으면 같은 연결의 두 번째 SQL은 실행되지 않습니다.
- [ ] 아무것도 보내지 않는 연결은 설정한 시간 뒤 서버가 닫습니다.
- [ ] 응답을 받기 전에 연결을 끊은 INSERT는 파일에 남아 있습니다.
