# 08: 100만 건 생성과 INDEX 대 SCAN 측정

**What to build:** 팀원이 명령 하나로 같은 100만 건 SQL 파일을 매번 만들고, Phase 1의 CLI로 그대로 넣고, 같은 엔진 세션에서 `id` 조회(INDEX)와 다른 field 조회(SCAN)의 속도 차이를 잽니다. 결과는 측정 기록 하나로 남고, B+ 트리 노드 크기도 이 측정으로 고릅니다. 결정은 `docs/prd/final.md` Phase 2 절의 데이터 생성과 측정을 따릅니다. 측정 시나리오는 앞으로 더 늘어날 예정이므로, 질의 세트를 쉽게 더할 수 있게 만듭니다.

**Blocked by:** 07

**Status:** ready-for-agent

작업에 포함되는 것:

- **생성 스크립트**: 행 수와 시드를 받아 INSERT 문이 든 SQL 파일을 만듭니다. 측정용 테이블은 `users(name TEXT, email TEXT, age INT)`입니다. 시드가 같으면 같은 파일이 나옵니다. `name`과 `email`은 번호로 만들어(`user0000123@example.com`) 값이 겹치지 않게 해서, `id` 조회와 다른 field 조회가 같은 record 1건을 돌려주게 합니다.
- **적재**: 측정마다 빈 테이블에서 시작해, 생성한 SQL 파일을 CLI(`-q`)로 일반 INSERT 경로로 넣습니다(L24, L26). 적재 시간을 적습니다.
- **`make bench`**: 엔진을 직접 링크한 측정 프로그램을 sanitizer 없이 `-O2`로 만듭니다. 조회 시간은 엔진 준비가 끝난 뒤부터 재므로 재구성 시간과 터미널 출력이 들어가지 않습니다. 재구성 시간은 따로 적습니다.
- **측정 절차**: 같은 엔진 세션에서 두 경로를 한 번씩 데운 뒤, SQL 문장 하나를 넘겨 결과를 받기까지 잽니다. INDEX는 1,000번(중앙값, p99), SCAN은 30번(중앙값, 최소, 최대)입니다.
- **질의 세트**: 같은 record를 `WHERE id = k`와 `WHERE email = '…'`로 찾는 쌍을 기본으로, 레코드 위치 앞·중간·뒤, 없는 값, 같은 ID를 강제로 SCAN한 경우를 더합니다. 강제 SCAN 경로는 측정 프로그램에서만 쓰고, 일반 SQL의 planner 규칙을 바꾸지 않습니다.
- **노드 크기**: 노드 크기 16, 32, 64, 128마다 ID 1\~1,000,000을 오름차순으로 트리에 넣고, 트리 높이, 노드 수, 메모리, 전체 삽입 시간, 무작위 키 1,000번 찾기의 중앙값과 p99를 적습니다. 결과로 상수를 정합니다. 오름차순 키에서는 왼쪽 리프가 절반만 찹니다. 메모리 비용이 문제가 되면 오른쪽 끝 분할을 다음 단계로 시험합니다.
- **측정 기록**: `CONVENTION.md` § 측정 기록에 따라 `docs/measurements/`에 파일 하나로 남깁니다. frontmatter에 `seq`, `topic`, `date`, `who`, `commit`, `previous`, `machine`, `build`, `command`, `records`를 적습니다. 본문에는 읽은 record 수, 트리 높이와 메모리, 저장 형식을 함께 적습니다.
- **문서**: `README.md`의 "성능 비교"에 결론과 측정 기록 링크만 둡니다. `docs/requirements.md`의 L23\~L26, L40, L41, L48(속도) 행을 채웁니다.

완료 조건:

- [ ] 같은 시드로 두 번 만든 SQL 파일이 바이트까지 같습니다.
- [ ] 100만 건 적재 뒤 `SELECT`가 100만 record를 셉니다.
- [ ] `make bench`가 질의 세트 전체의 통계와 노드 크기 비교를 출력합니다.
- [ ] 측정의 모든 쌍에서 INDEX 결과와 SCAN 결과가 같은 record입니다.
- [ ] 측정 기록 파일이 규칙대로 있고, 노드 크기 상수가 그 기록의 결론과 같습니다.
