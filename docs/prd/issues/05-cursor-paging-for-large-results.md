# 05: 1만 건이 넘는 SELECT 결과를 커서로 나눠 받기

**Status:** ready-for-agent

**What to build:** HTTP SELECT 결과가 1만 건을 넘으면 서버가 처음 1만 건과 다음 위치(커서)를 돌려주고, 클라이언트가 커서를 붙여 같은 SQL을 다시 보내 다음 부분을 받습니다. 회의(2026-11-16)에서 결과 전달은 DA 설계(결과를 모아 JSON 하나로 보냄, `docs/prd/DA.md` 3.3과 7.3)로 정했고, 1만 건이 넘으면 잘라서 받기로 했습니다. 한 응답에 조각을 이어 보내는 방식은 LMH의 순차 전송(`docs/PRD.md` 135줄)과 같은 구조라서 전송이 끝날 때까지 읽기 잠금을 쥡니다. 그래서 고르지 않았습니다. 팀은 이 설계를 구현할 때 검증할 영역으로 정했습니다. 아래 "검증할 주장"이 그 대상입니다.

우선순위: 기본선 뒤.

**Blocked by:** 02 (`committed_size`를 씁니다)

## API

- SELECT 응답에 `"next_cursor": <정수>`가 붙을 수 있습니다. 정수는 SCAN이 아직 읽지 않은 다음 레코드의 바이트 위치입니다.
- 클라이언트는 같은 SQL을 `POST /query?cursor=<정수>`로 다시 보냅니다. 본문은 그대로 SQL입니다.
- SCAN이 `committed_size`(티켓 02)에 닿으면 응답에 `next_cursor`가 없습니다.
- 한 번에 보내는 양은 1만 건 또는 결과 바이트 상한 중 먼저 닿는 쪽까지입니다.
- 1만 건을 넘는 결과는 더 이상 `400 result_too_large`가 아닙니다. 이 오류는 레코드 하나가 바이트 상한보다 클 때만 남습니다.
- CLI는 나눠 받지 않습니다. CLI에는 결과 상한이 없습니다(`docs/prd/DA.md` 113줄).

## 엔진 변경

서버용 함수를 하나 더합니다. CLI가 쓰는 `engine_execute`는 그대로입니다.

```c
struct engine_result *engine_execute_page(struct engine *engine, const char *sql,
                                          uint64_t cursor);
```

함수 이름은 예시입니다. SCAN은 `cursor`에서 시작해 상한에서 멈춥니다. 읽기 잠금은 그 부분을 읽는 동안만 쥡니다.

## 커서 검사

커서는 레코드가 시작하는 위치여야 합니다. 그 위치의 레코드를 읽고, 그 `id`를 B+ 트리에서 찾습니다. 트리가 같은 위치를 돌려주면 올바른 커서입니다. 읽기 한 번과 트리 조회 한 번이면 됩니다.

아래 경우는 새 오류 이유 `400 invalid_cursor`로 답합니다.

- 레코드 시작이 아닌 위치
- `committed_size`보다 큰 위치
- 0 이상의 정수가 아닌 값
- INDEX 경로를 쓰는 질의에 붙은 커서. INDEX 질의는 결과가 많아야 1건이라 나눌 일이 없습니다.

## 검증할 주장

이 설계는 한 가지 성질에 기댑니다. 테이블 파일은 덧붙이기만 하고, 기본선에는 UPDATE와 DELETE가 없습니다.

1. 부분 사이에 INSERT가 없으면, 부분들을 이은 결과가 SCAN 한 번의 결과와 같습니다.
2. 부분 사이에 INSERT가 있으면, 새 레코드는 조건에 맞을 때 뒤 부분에만 나옵니다. 앞서 받은 레코드가 다시 나오거나 빠지지 않습니다.
3. 부분 하나를 읽는 동안만 읽기 잠금을 쥡니다.
4. 1만 건 한 부분의 메모리와 응답 시간을 재서 상한 1만이 적당한지 정합니다.

부분들은 한 시점의 스냅샷이 아닙니다. UPDATE나 DELETE를 범위에 넣으면 이 설계를 다시 검토합니다.

## 테스트로 확인할 것

- 주장 1과 2를 실제 서버에 대한 기능 테스트로 확인합니다.
- 잘못된 커서 경우마다 `400 invalid_cursor`가 나옵니다.
- 정확히 1만 건인 결과에는 `next_cursor`가 없고, 10,001건이면 `next_cursor`가 있으며 두 번째 부분은 1건입니다.
