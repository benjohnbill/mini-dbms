# 04: 시작할 때 깨진 테이블 파일을 찾아 멈추기

**What to build:** 테이블 파일 끝이 잘렸거나 중간이 손상되었으면, 엔진이 시작을 멈추고 파일 이름, 바이트 위치, record 번호, 종류(`잘림` 또는 `손상`)를 알립니다. 파일은 고치지 않습니다. 회의(2026-11-16)에서 저장 형식을 길이를 앞에 붙인 바이너리로 정했기 때문에, DA 초안의 "마지막 record에 `\n`이 없으면 잘린 것" 규칙은 쓸 수 없습니다. 이 티켓이 그 규칙을 대신합니다. 판정 규칙은 회의에서 AI에게 맡긴 결정입니다. 팀이 다르게 정하면 바꿉니다.

**Blocked by:** 03

**Status:** ready-for-agent

## 판정 규칙

스키마에서 테이블마다 두 값을 계산합니다.

- `min_body` = 8 + 8 × (`INT` field 수) + 4 × (`TEXT` field 수). 모든 `TEXT`가 빈 문자열일 때입니다.
- `max_body` = `min_body` + 1 MiB × (`TEXT` field 수). 모든 `TEXT`가 최대 길이일 때입니다.

티켓 03의 시작할 때 읽기에서, 파일 크기를 `S`, 읽는 위치를 `o`로 두고 record마다 확인합니다.

1. `o == S`이면 끝입니다.
2. `S - o < 4`이면 길이 칸이 잘렸습니다. `잘림`입니다.
3. 본문 길이가 `min_body`보다 작거나 `max_body`보다 크면 `손상`입니다.
4. `o + 4 + 본문 길이 > S`이면 record가 파일 끝을 넘습니다. 남은 바이트로 field를 읽어 봅니다. 남은 바이트 안에서 모든 field가 다 읽히면 길이 칸이 내용과 맞지 않는 것이므로 `손상`입니다. 다 읽히지 않으면 `잘림`입니다. INSERT는 record를 write 한 번으로 붙이므로, 잘린 끝은 진짜 record의 앞부분입니다.
5. field가 본문 길이를 정확히 다 써야 합니다. 남거나 모자라면 `손상`입니다.
6. `id`는 앞 record의 `id`보다 커야 하고, 첫 `id`는 1 이상이어야 합니다. 아니면 `손상`입니다.
7. `o = o + 4 + 본문 길이`로 옮겨 계속합니다.

```text
data/users.tbl: 1520번째 바이트의 record(38번째)가 깨졌습니다: 잘림 (record 중간에서 파일이 끝남)
```

## 기본선에는 CRC를 넣지 않음

- CRC는 파일을 자동으로 고칠 때 쓸모가 있습니다. 기본선은 멈추고 알리기만 합니다.
- CJG 시험 엔진에서 CRC 계산이 SCAN 시간의 약 60%였습니다. CRC를 넣으면 INDEX와 SCAN 비교에 체크섬 비용이 섞입니다.
- LMH 초안은 체크섬 손상 감지를 범위 밖으로 두었습니다.

자동 복구를 차별점으로 넣을 때 CRC도 같이 넣습니다.

## 문서

`README.md`의 "알려진 한계"에 두 줄을 더합니다. "길이 칸은 맞고 `TEXT` 바이트만 바뀐 손상은 찾지 못한다", "깨진 테이블 파일은 사람이 고쳐야 다시 시작한다".

완료 조건:

- [ ] 빈 테이블 파일은 정상이고 다음 ID는 1입니다.
- [ ] 마지막 길이 칸 중간(1~3바이트)에서 끝난 파일은 `잘림`으로 시작이 멈춥니다.
- [ ] 마지막 본문 중간에서 끝난 파일은 `잘림`으로 시작이 멈춥니다.
- [ ] 길이 칸이 파일 끝을 넘는 중간 record는 `잘림`이 아니라 `손상`입니다.
- [ ] 길이가 0인 record는 `손상`입니다. 0으로 채워진 끝이 이 경우입니다.
- [ ] field가 본문 길이보다 적게 또는 많게 쓰는 record는 `손상`입니다.
- [ ] 앞 record보다 작거나 같은 `id`는 `손상`입니다.
- [ ] 실패한 뒤 파일 크기와 내용이 그대로입니다.
- [ ] 메시지에 파일 이름, 바이트 위치, record 번호, 종류가 있고 CLI 종료 코드는 1입니다.
