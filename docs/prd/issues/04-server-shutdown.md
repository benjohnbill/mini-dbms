# 04: API 서버 종료

**What to build:** SIGINT를 받은 서버가 받은 요청을 끝까지 처리하고 자원을 정해진 순서로 정리한 뒤 끝납니다. 회의(2026-11-16)에서 HTTP는 Mongoose 7.23으로 정했고, 종료는 DA 설계(`docs/prd/DA.md` 7.5)를 출발점으로 이 티켓에서 검토하기로 했습니다. LMH 초안은 시간 제한 없이 기다립니다(`docs/PRD.md` 146줄).

아래 "팀이 정할 것" 세 가지가 정해지면 `**Status:** ready-for-agent`를 붙입니다.

**Blocked by:** None (can start immediately)

## 제안하는 순서 (DA 설계)

```text
SIGINT
  → 시그널 핸들러는 플래그만 세움
  → 이벤트 루프가 플래그를 보고 듣기 연결을 닫음
  → 이벤트 루프를 계속 돌리며 끝난 작업의 응답을 보냄
  → 작업 대기열이 비고 작업 스레드가 모두 쉬면
      남은 응답 전송을 최대 5초 기다림
  → 모든 연결을 닫음
  → 작업 스레드를 멈추고 join
  → Mongoose 매니저 해제
  → engine_destroy (flock 해제)
  → 종료 코드 0
```

이 순서인 이유(`docs/prd/DA.md` 382~384줄):

- 응답은 이벤트 루프만 보낼 수 있습니다. 작업이 모두 끝날 때까지 이벤트 루프를 멈추지 않습니다.
- 작업 스레드는 매니저에 `mg_wakeup`을 부릅니다. 작업 스레드가 모두 멈춘 뒤에 매니저를 해제해야 합니다. 순서가 반대면 해제된 메모리를 씁니다.
- 5초는 전송을 기다리는 시간이지 종료 전체의 시간이 아닙니다. 긴 SCAN이 있으면 종료가 더 걸립니다.

## 팀이 정할 것

1. **SIGINT 뒤 keep-alive 연결로 새 요청이 오면.** 제안: `503`과 새 오류 이유 `shutting_down`, `Connection: close`로 답합니다. DA 오류 표에는 아직 이 이유가 없습니다.
2. **SIGINT가 한 번 더 오면.** 제안: 바로 끝냅니다. 쓰는 중이던 INSERT가 있으면 마지막 레코드가 잘릴 수 있고, 다음 시작에서 01이 멈추고 사람이 파일을 고칩니다. 다른 안은 두 번째 SIGINT를 무시하는 것입니다.
3. **5초 상한 또는 무기한.** DA는 5초, LMH는 무기한입니다. 추천: 5초. 느린 클라이언트 하나가 프로세스를 붙잡지 못하게 하기 위해서입니다.

## 테스트로 확인할 것

- SIGINT 때 실행 중이던 SELECT는 전체 응답을 받습니다.
- SIGINT 전에 받은 INSERT는 종료 뒤 파일에 남아 있습니다.
- SIGINT 뒤의 새 TCP 연결은 거절됩니다.
- 종료 코드는 0입니다.
- 종료 뒤 같은 데이터 폴더로 두 번째 프로세스가 뜹니다. flock이 풀렸다는 뜻입니다.
- 응답을 읽지 않는 클라이언트는 마지막 작업이 끝난 뒤 최대 5초만 종료를 늦춥니다.
- 종료 테스트를 `make tsan`에서도 돌립니다.
