# PRD 초안 — CJG

> 2026-11-16, 팀 회의 전 초안입니다. 표시가 없는 결정은 모두 **추천, 검토 전**입니다. 회의에서 견주어 바꿀 수 있습니다. 최종 PRD(`docs/prd/final.md`)가 나온 뒤에는 이 파일을 고치지 않습니다.

## 1. 문제: 왜 DBMS인가

앱이 데이터를 파일에 직접 쓰고 읽으면, 데이터를 **무엇**을 찾는지와 **어떻게** 찾는지가 앱 코드 안에 섞입니다. 찾는 방법을 바꾸려면(예: 인덱스 추가) 앱 코드를 고쳐야 합니다.

> SQL은 무엇을 원하는지만 말하고, DB는 그 문장을 끊고 구조로 정리한 뒤, 그 구조를 보고 어떻게 찾을지(INDEX 또는 SCAN)를 스스로 정해 실행한다.

이 분리를 데이터 독립성(Codd, 1970)이라고 합니다. 확인한 예: 같은 SQL `SELECT * FROM users WHERE name = ?`를 100만 행에 보냈을 때, `name`에 인덱스를 추가하기 전에는 116.202 ms, 추가한 뒤에는 0.048 ms가 걸렸습니다. 앱 코드는 한 줄도 바뀌지 않았습니다(SQLite로 잰 개인 실험). 시험 구현한 우리 엔진에서는 100만 건에서 `WHERE id = ?`(INDEX)가 중앙값 0.0046 ms, `WHERE name = ?`(SCAN)가 127.46 ms였습니다(`CJG-engine` 브랜치의 `docs/measurements/001-CJG-index-vs-scan.md`).

## 2. 해결

SQL 문장을 받아 파일에 저장하고 읽는 엔진을 만들고(Phase 1), `id`로 찾을 때는 메모리 B+ 트리를 쓰고(Phase 2), 그 엔진을 스레드 풀 API 서버로 감쌉니다(Phase 3).

```text
SQL 텍스트
  → tokenizer (단어로 끊기)
  → parser    (문법 검사, AST 만들기)
  → planner   (INDEX 또는 SCAN 결정)
  → 실행       (테이블 파일 읽기와 쓰기, B+ 트리 찾기)
```

언어: C (팀 결정, 2026-11-16). mini-redis의 도구(make, 테스트 헤더)를 다시 쓰고, pthread로 실제 스레드 풀을 만들 수 있습니다.

## 3. 범위

두 층으로 나눕니다. 회의의 첫 안건은 "기본선만 할지, 어디까지 갈지"입니다.

| 층 | 내용 |
|---|---|
| 기본선 (팀 범위) | LMS Phase 1\~3. `INSERT`, `SELECT`(전체, `WHERE 컬럼 = 값`), 자동 `id`, 100만 건 측정, 스레드 풀 API 서버 |
| 목표 | 실제로 쓸 수 있는 DBMS. 첫 사용처는 mini-redis 상품 데모의 원본 DB 자리입니다 |

- 외부 사용처가 있으므로, API를 특정 client에 묶지 않습니다.
- 하지 않는 것: `CREATE TABLE`(L19, 스키마 파일로 대신합니다), 트랜잭션, `JOIN`.
- 팀 범위 밖에서 나중에 더할 것: 범위 검색, `UPDATE`, `DELETE`, `ORDER BY`, 집계. 팀에는 "SQL 종류를 나중에 더하기 쉬운 처리기 구조"만 요청합니다.

## 4. 핵심 문제 표

LMS 중점 포인트(L35\~L44)마다 문제의 정의와 해결을 적습니다.

| # | 핵심 문제 | LMS | 내 정의 | 내 해결 (추천, 검토 전) | 실제 DBMS의 답 | 회의에 가져갈 트레이드오프 |
|---|---|---|---|---|---|---|
| 1 | SQL 텍스트 → 구조 → 동작 | L35 L37 L38 | 글자 덩어리를 엔진이 이해하는 구조로 바꾸고, 그 구조로 동작을 고르는 문제 | 직접 쓴 tokenizer와 재귀 하강 parser → AST → 문장 종류마다 실행 함수 하나. 행 읽기는 iterator 모양. CLI는 SQL 파일을 받아 한 문장씩 실행 | PostgreSQL은 bison, SQLite는 Lemon(parser 생성기)으로 parse tree를 만들고, PostgreSQL은 계획 나무로, SQLite는 바이트코드로 바꿔 실행 | 직접 쓴 parser vs parser 생성기. AST 없이 바로 실행 vs AST |
| 2 | 파일 안의 레코드 형식 | L36 | 레코드를 파일에 어떤 바이트로 적어야 다시 읽을 수 있고, 중간에 꺼져도 망가지지 않는가 | 테이블마다 바이너리 파일 하나, 뒤에 붙이기만 함. 레코드마다 헤더(길이, 삭제 표시 1바이트, 체크섬). 타입은 `INT`(64비트), `TEXT`(가변 길이). 스키마는 데이터 폴더의 사람이 읽는 파일 하나 | SQLite와 PostgreSQL은 고정 크기 페이지로 파일을 나누고 페이지 안에 레코드를 넣음. Bitcask는 뒤에 붙이기만 하는 로그 | 텍스트(CSV) vs 바이너리. 붙이기만 vs 페이지 |
| 3 | B+ 트리로 `id` 찾기 | L39 | `WHERE id = ?`를 모든 레코드를 읽지 않고 찾는 문제 | 메모리 B+ 트리, 키는 `id`, 값은 파일 안 위치(offset). planner가 조건이 `id`면 INDEX, 다른 컬럼이면 SCAN. 리프끼리 이어서 범위 검색도 가능 | 디스크 페이지 기반 B+ 트리. 리프 연결로 범위 검색 | 노드 크기(한 노드의 키 개수) |
| 4 | 100만 건 생성과 측정 | L40 | 대량 데이터를 빨리 넣고, 공정하게 재는 문제 | 생성 스크립트가 SQL 파일을 만들고 CLI로 넣음. 측정은 같은 엔진, 같은 프로세스에서 한 번 데운 뒤 INDEX와 SCAN을 잼 | 대량 삽입은 트랜잭션 하나로 묶거나 전용 명령(PostgreSQL `COPY`)을 씀 | `fsync`를 매번 vs 묶어서 |
| 5 | 인덱스와 파일이 어긋나지 않기 | L41 | B+ 트리는 메모리에 있으므로, 프로그램이 꺼지면 사라지고 파일과 달라질 수 있는 문제 | 파일이 원본. 시작할 때 파일을 처음부터 읽어 B+ 트리를 다시 만듦. 체크섬이 깨진 마지막 레코드는 버림(`INSERT` 하나의 크래시 원자성). 다음 `id`도 이때 알아냄 | Bitcask도 시작할 때 파일로 메모리 인덱스를 다시 만듦. SQLite와 PostgreSQL은 인덱스도 파일에 두고 저널이나 WAL로 함께 맞춤 | 시작 시 재구성 시간 vs 인덱스 파일 저장 |
| 6 | 여러 스레드, 엔진 하나 | L42 | 동시에 들어온 요청이 같은 파일과 B+ 트리를 고칠 때 데이터가 깨지는 문제 | 기본선은 테이블 잠금 하나. 쓰기 하나가 끝날 때까지 다른 요청이 기다림 | SQLite는 쓰기 하나만 허용하는 잠금, PostgreSQL은 MVCC와 행 잠금 | 잠금 하나 vs 읽기와 쓰기 잠금 분리 |
| 7 | 엔진과 API 서버의 경계 | L43 L44 | 엔진과 서버가 서로를 얼마나 알아야 하는가 | 엔진은 `execute(sql) → 결과` 함수 하나만 밖에 보이는 라이브러리. 서버는 요청을 받아 스레드 풀에 넘기고 그 함수를 부름. 프로토콜은 HTTP `POST /query`(curl로도 부를 수 있게) | SQLite는 서버 없는 라이브러리. PostgreSQL은 자체 프로토콜, 연결마다 프로세스 하나 | 스레드 풀 크기. HTTP vs 자체 TCP 프로토콜 |

## 5. 범용 추가 기능

다른 팀과의 차별점(L34)입니다. 우선순위 순서입니다.

1. `EXPLAIN`: 쿼리마다 INDEX인지 SCAN인지 출력합니다. "어떻게"를 엔진이 정한다는 1절을 눈으로 보여 줍니다.
2. 두 번째 인덱스: `id`가 아닌 컬럼에도 B+ 트리를 둡니다. 시험 구현에서 바뀐 로직은 planner가 중심이었고, 테이블이 새 트리를 유지하는 코드도 함께 늘었습니다(8절).
3. 저널: 여러 레코드를 한 번에 쓰다가 꺼져도 전부 또는 전무가 되게 합니다.

## 6. 조정할 트레이드오프

지금은 나열만 합니다. 회의에서 하나씩 정합니다.

- `fsync`를 레코드마다 vs 묶어서: 영속성 대 속도입니다. `fsync`는 원자성이 아니라 영속성의 장치입니다.
- 텍스트 vs 바이너리 레코드 형식
- 테이블 잠금 하나 vs 읽기와 쓰기 잠금 분리
- 스레드 풀 크기
- B+ 트리 노드 크기

## 7. 테스트 결정

- 단위 테스트(L45): tokenizer, parser, B+ 트리(삽입, 분할, 찾기, 범위), 레코드 인코딩과 디코딩, HTTP 요청 파싱, 스레드 풀.
- 기능 테스트(L46, L47): SQL 파일을 CLI로 실행하고 출력을 비교합니다. 서버를 띄워 HTTP로 보낸 요청의 응답 코드와 JSON도 비교합니다.
- 인덱스 비교(L25, L48): 같은 엔진, 같은 프로세스, 한 번 데운 뒤 `id` 조건과 다른 컬럼 조건을 잽니다. 결과는 `docs/measurements/`에 남깁니다.
- 크래시 복구: 마지막 레코드를 일부러 잘라 낸 파일로 시작해도 앞 레코드가 모두 읽히는지 봅니다. 가운데 레코드가 깨진 파일은 열기를 거절하고 파일을 고치지 않는지, 여러 행 `INSERT` 도중 프로세스가 죽으면 다시 열 때 그 행이 하나도 남지 않는지도 봅니다.
- 동시성(L49): 여러 스레드가 동시에 `INSERT`한 뒤 레코드 수가 보낸 수와 같은지 봅니다.
- 엣지 케이스(L50)는 테스트 이름으로 남깁니다.

## 8. Phase별 설계

### Phase 1: SQL 처리기와 파일

| 결정 | 고른 것 | 이유와 대가 |
|---|---|---|
| 처리기 구조 | 직접 쓴 tokenizer → 재귀 하강 parser → AST → 문장 종류마다 실행 함수 하나 | 코드를 끝까지 읽을 수 있고 SQL 종류를 더하기 쉽습니다. 문법이 커지면 parser 코드도 길어집니다 |
| 행 읽기 | `RowSource` iterator(`next`, `close`) | 실행기는 SCAN인지 INDEX인지 모르고 다음 행만 받습니다. planner가 고른 방식만 갈아 끼웁니다 |
| 파일 형식 | 테이블마다 바이너리 파일 하나, 뒤에 붙이기만 합니다. 레코드 헤더 9바이트(길이 4, 삭제 표시 1, CRC32 4), 본문 최대 1 MiB | 쓰기가 단순하고, 꺼진 뒤 깨진 끝을 체크섬으로 찾습니다. 사람이 직접 읽을 수 없고, 지운 행의 자리는 돌아오지 않습니다 |
| 스키마 | 데이터 폴더의 `schema.txt`, 테이블 하나에 한 줄(`users id:INT name:TEXT age:INT`) | `CREATE TABLE`이 필요 없습니다(L19) |
| 타입 | `INT`(64비트), `TEXT`(가변 길이). NULL은 없습니다 | 범위를 좁혀 엣지 케이스를 줄입니다 |
| `INSERT` 규칙 | `id`를 뺀 모든 컬럼에 값이 필요합니다. `id`를 직접 주면 오류입니다. 여러 행 `VALUES (...),(...)`를 지원합니다 | 자동 id(L22)만 허용합니다. id를 직접 넣는 사용처(상품 데모)는 어댑터가 맞춥니다 |
| CLI | `cli <데이터 폴더> <SQL 파일>`, `-`면 표준 입력, `-q`면 INSERT 결과를 숨깁니다 | 100만 건을 SQL 파일로 넣을 때 출력이 병목이 되지 않게 합니다 |

### Phase 2: B+ 트리

| 결정 | 고른 것 | 이유와 대가 |
|---|---|---|
| 인덱스 | 메모리 B+ 트리, 키 `id` → 값 파일 offset, 리프끼리 연결, 노드당 키 최대 64개 | L21이 메모리 방식입니다. 리프 연결로 범위 검색이 됩니다 |
| 파일과 인덱스 맞추기(L41) | 파일이 원본입니다. 열 때 파일을 끝까지 읽어 트리를 다시 만들고, 다음 `id`도 이때 정합니다 | 인덱스 파일이 없어 둘이 어긋날 수 없습니다. 100만 건에서 열기마다 약 0.3\~0.4초가 듭니다 |
| 깨진 레코드 | 마지막 레코드가 깨졌으면 잘라 냅니다. 중간 레코드가 깨졌으면 열기를 거절하고 파일을 고치지 않습니다 | 끝은 쓰다가 꺼진 흔적이라 버려도 안전합니다. 중간은 진짜 손상이라 사람이 봐야 합니다. 길이 칸이 파일 끝을 넘으면, 남은 바이트로 모든 컬럼을 읽을 수 있을 때 손상으로 보고 열기를 거절합니다. 레코드는 한 번의 write로 붙으므로 잘린 끝은 진짜 레코드의 앞부분이기 때문입니다. 대가로, 0으로 채워진 끝은 자동으로 잘리지 않고 사람이 고쳐야 합니다 |
| planner 규칙 | `WHERE id = ?` 또는 인덱스가 있는 컬럼의 `=`이면 INDEX, 그 밖은 SCAN | "어떻게"를 엔진이 정하는 자리입니다(1절) |
| 인덱스 결과 재비교 | INDEX로 찾은 행도 조건과 한 번 더 비교합니다 | 결과가 항상 맞습니다. 대신 인덱스 버그가 엔진 수준에서 가려져, B+ 트리 단위 테스트만 그 버그를 잡습니다 |
| 측정 | 같은 프로세스에서 한 번 데운 뒤 `id` 조회 1000번, `name` 조회 10번의 중앙값 | INDEX와 SCAN 차이만 남깁니다. 파일이 페이지 캐시에 있으므로 디스크 I/O 비교가 아니라 CPU 비교입니다. SCAN 시간의 약 60%는 레코드마다 하는 CRC 계산입니다 |

### Phase 3: API 서버

| 결정 | 고른 것 | 이유와 대가 |
|---|---|---|
| 엔진과 서버의 경계(L43) | 서버는 `engine_execute(sql)` 하나만 부릅니다. CLI도 같은 엔진을 씁니다 | 서버를 바꿔도 엔진은 그대로입니다 |
| 프로토콜 | HTTP `POST /query`, 본문은 SQL, 답은 JSON. 연결 하나에 요청 하나(`Connection: close`) | `curl`로 어느 언어에서나 부릅니다. 연결을 매번 새로 맺는 비용이 있습니다 |
| HTTP 구현 | 직접 작성했습니다. mini-redis의 mongoose는 쓰지 않았습니다 | GPL 의존성을 피합니다. 대신 요청 파싱의 엣지 케이스를 직접 막아야 합니다 |
| 응답 코드 | SQL 오류 400, 없는 경로 404, POST가 아니면 405, 본문 1 MiB 초과 413, 대기열이 차면 503 | 클라이언트가 실패 이유를 코드로 구분합니다 |
| 스레드 풀 | 기본 스레드 8개, 대기열 128칸(서버 인자로 바꿉니다) | 요청이 몰려도 메모리가 끝없이 늘지 않습니다 |
| 동시성(L42) | 테이블 잠금(mutex) 하나를 문장 단위로 잡습니다. 읽기와 쓰기가 같은 잠금을 씁니다 | 데이터가 깨질 일이 가장 적습니다. SELECT끼리도 줄을 섭니다 |
| 수신 제한 | 헤더 8 KiB, `recv` 한 번마다 5초 | 큰 요청과 멈춘 연결을 막습니다. 1바이트씩 천천히 보내는 클라이언트는 아직 막지 못합니다 |

### 영속성과 추가 기능

| 결정 | 고른 것 | 이유와 대가 |
|---|---|---|
| `fsync` | 한 행 `INSERT`는 `fsync`하지 않습니다. 여러 행 `INSERT`는 저널과 데이터를 `fsync`합니다 | 프로세스가 죽어도 안전하고, 100만 건 적재가 2.25초입니다. 정전 때는 방금 응답한 행을 잃을 수 있습니다(6절 트레이드오프) |
