# 미니 DBMS 개인 PRD

상태: 작성 중. 팀 회의에서 다른 개인안과 비교할 초안이다. 아래 필수 요구사항 외의 세부 동작과 설계는 그릴링을 거쳐 결정한다.

## 목표

C로 파일 기반 SQL 처리기, 메모리 기반 B+ 트리 인덱스, 스레드 풀 기반 API 서버를 연결한 미니 DBMS를 구현한다. SQL 입력부터 저장·인덱스·병렬 API 처리까지의 흐름을 구현하고, 동작과 성능을 검증해 설명할 수 있는 프로젝트를 만든다.

## 과제의 필수 요구사항

### Phase 1: SQL 처리기

- CLI로 SQL 텍스트 파일을 전달한다.
- 최소 `INSERT`와 `SELECT`를 파싱하고 실행한다.
- 테이블을 파일로 관리하고, 삽입 시 파일에 추가하며 조회 시 파일을 읽는다.
- 스키마와 테이블은 이미 존재한다고 가정한다. `CREATE TABLE`은 필수가 아니다.

### Phase 2: B+ 트리 인덱스

- 삽입 시 ID를 자동 부여하고 메모리 기반 B+ 트리에 등록한다.
- ID 기준 조회는 인덱스를 사용한다.
- Phase 1 SQL 처리기를 사용하여 100만 건 이상을 삽입하고, ID 인덱스 조회와 다른 필드 선형 조회의 성능을 비교한다.

### Phase 3: API 서버

- 외부 클라이언트가 API를 통해 DBMS를 사용할 수 있다.
- 스레드 풀로 SQL 요청을 병렬 처리한다.
- Phase 1과 Phase 2를 내부 DB 엔진으로 활용한다.

## 지원 환경

- macOS 네이티브와 Windows의 WSL 2 Linux 환경을 지원한다. 두 환경에서 빌드와 핵심 기능을 검증한다.
- Windows 네이티브 실행은 지원 범위에서 제외한다. 팀원별 WSL 2 설치와 사용 가능 여부는 확인이 필요하다.
- macOS와 WSL 2 모두에서 빌드, 단위 테스트, SQL 파일 실행, 재시작 후 조회, API와 동시성 기능을 검증한다. 100만 건 성능 비교는 우선 한 환경에서 수행하며 환경별 결과는 구분한다.
- macOS와 WSL 2 사이에서 테이블 데이터 파일을 공유할 수 있어야 한다. 정수 크기·바이트 순서 등 저장 형식은 두 환경에서 동일하게 해석되도록 정의한다.

## 실행과 빌드

- CLI와 서버는 실행 시 데이터 디렉터리를 전달받아 그 안의 사전 준비된 스키마와 테이블 파일을 찾는다. 프로젝트에 예제 스키마와 빈 테이블 파일을 제공하며, 데이터 디렉터리 준비 방법과 사용자가 스키마를 작성할 수 있도록 파일 형식을 문서화한다. 구체적인 인자와 파일 배치는 미결이다.
- 빌드, 일반 테스트, 대용량 성능 비교에 각각 별도의 실행 명령을 제공한다. 명령 이름과 빌드 도구는 미결이다.

## 품질과 검증

- 단위 테스트와 각 Phase의 기능 테스트를 수행한다.
- Phase 2는 인덱스 정확성과 성능 비교를 검증하고, Phase 3은 API 기능을 검증한다.
- 엣지 케이스를 고려하고 핵심 로직을 설명할 수 있어야 한다.

## Phase 간 연결

1. Phase 1은 SQL 파일을 순차 실행하는 CLI와 스키마·테이블 파일을 사용하는 SQL 엔진을 제공하며 삽입 시 테이블별 자동 ID를 부여한다. 이 단계의 조회는 선형 탐색을 사용한다. 정상 종료 후 재시작해도 저장된 행을 조회한다. CLI와 HTTP 서버는 같은 SQL 엔진을 호출하고, 엔진은 테이블 파일과 인덱스에 접근한다.
2. Phase 2는 같은 엔진에 테이블별 ID 인덱스로 메모리 B+ 트리를 연결한다. Phase 1에서 자동 부여해 저장한 ID와 기존 데이터를 그대로 사용해 인덱스를 구축하며, ID 동등 조건은 인덱스를, 다른 열의 동등 조건은 선형 탐색을 사용한다. Phase 1에서 지원한 SQL 문법과 저장·조회 동작을 유지하면서 인덱스를 추가한다.
3. Phase 3은 Phase 2 엔진을 HTTP 서버에서 재사용한다. 요청 처리는 스레드 풀을 사용하며 테이블별 읽기·쓰기 동시성 규칙을 지킨다. CLI와 서버는 동일 데이터 디렉터리를 동시에 사용하지 않는다.

## 차별화 요소

- **재현 가능한 성능 비교 도구:** 100만 건 이상을 생성해 SQL 처리기로 삽입하고, 인덱스 조회와 선형 탐색을 반복 실행하며 정확성과 측정 결과를 기록한다. 기본 비교에서는 이름도 행마다 다르게 생성해 ID와 이름 조회가 같은 한 행을 반환하도록 한다. 존재하지 않는 값과 테이블의 앞·중간·뒤에 있는 값도 조회한다. 데이터 분포·조회 조건·측정 구간·실행 환경과 데이터 저장 위치를 함께 남겨 다른 사람이 비교를 다시 실행할 수 있게 한다. 같은 ID의 인덱스·선형 비교를 위한 선형 조회 경로는 검증·측정용으로 제공하며 일반 SQL의 ID 인덱스 사용 규칙을 바꾸지 않는다. 구체적인 명령과 결과 형식은 미결이다.

## 검토한 대안

- **JOIN:** 여러 테이블을 연결하는 조회는 범위가 넓어져 제외했다. 각 SQL 문장은 한 테이블을 대상으로 한다.
- **스키마 제공:** 코드에 고정하는 방식과 별도 파일을 비교하고, 테이블 정의를 별도로 제공하기 위해 파일을 선택했다.
- **테이블 저장:** 텍스트와 길이 정보를 담는 바이너리를 비교하고, 가변 길이 데이터의 경계와 레코드 위치를 다루기 위해 바이너리를 선택했다.
- **API:** 직접 정의한 TCP 프로토콜과 HTTP를 비교하고, 외부 클라이언트에서 시험하기 쉬운 HTTP를 선택했다.
- **트랜잭션:** 여러 문장을 묶는 명시적 트랜잭션은 파일·인덱스와 동시성까지 범위가 넓어져 선택 확장으로 두었다.

## 결정 사항

이 절에는 과제에서 명시하지 않은 개인 설계 선택과 추가 품질 목표도 포함된다.

### SQL과 CLI

- **미등록 테이블:** 스키마가 없는 테이블을 요청하면 존재하지 않는 테이블 오류를 반환하고 스키마나 테이블 파일을 생성하지 않는다.
- **INSERT 행 수:** 한 INSERT 문장은 한 행만 삽입한다. 여러 행을 하나의 VALUES 절로 삽입하는 문법은 지원하지 않는다. 대량 데이터는 여러 INSERT 문장으로 삽입한다.
- **INSERT 열 목록:** INSERT에는 열 이름 목록을 반드시 명시해야 한다. SQL의 열 순서가 스키마 순서와 달라도 허용하며 값을 열 이름에 대응시킨다. 열 목록을 생략한 INSERT는 지원하지 않는다.
- **기본 입력 검증 (검토 필요):** INSERT의 열 개수와 값 개수가 다르거나 존재하지 않는 열을 지정하면 오류로 거부한다. 지원하지 않는 SQL 문법, 정수 범위 초과, 닫히지 않은 문자열 및 종결되지 않은 문장도 오류로 거부한다. 빈 SQL 파일은 정상 종료한다.
- **대용량 SQL 파일:** SQL 파일 전체를 한꺼번에 메모리에 올리지 않고 문장을 읽어 순서대로 실행한다.
- **중복 INSERT 열:** 같은 열을 한 INSERT 문에서 두 번 지정하면 오류로 거부한다.
- **WHERE 자료형:** 조건 값과 열의 자료형이 다르면 자동 변환하지 않고 오류로 거부한다.
- **CLI 결과:** 각 문장의 조회 또는 삽입 성공 결과를 실행 순서대로 출력한다. 오류가 나면 내용을 출력하고 0이 아닌 종료 코드로 종료한다. 출력 서식은 미결이다.
- **문자열 인코딩:** UTF-8을 사용하며 잘못된 UTF-8 입력과 문자열 값에 포함된 널 바이트(U+0000)는 CLI와 HTTP 모두에서 오류로 거부한다. 문자열 값 하나는 UTF-8 인코딩 기준 최대 1 MiB이며 초과하면 오류로 거부한다. HTTP에는 별도의 본문 전체 1 MiB 제한이 적용되므로 실제로 전달할 수 있는 값은 요청 내용에 따라 더 작다.
- **식별자 형식:** 테이블과 열 이름은 영문자 또는 `_`로 시작하고 나머지는 영문자·숫자·`_`만 허용한다. 따옴표로 감싼 식별자 문법은 지원하지 않는다.
- **SQL 키워드:** SQL 키워드는 대소문자를 구분하지 않는다. 테이블·열 이름 및 문자열 값의 대소문자 규칙은 별도 결정에 따른다.
- **정수 범위:** 부호 있는 32비트 정수를 지원하고 범위 밖의 값은 오류로 거부한다. 일반 정수 범위는 -2,147,483,648부터 2,147,483,647까지이며 자동 ID는 1부터 2,147,483,647까지 사용한다. HTTP 응답에서는 정수와 ID를 JSON 숫자로 전달한다.
- **빈 SQL 문장:** CLI의 SQL 파일에서 빈 문장과 공백만 있는 부분은 무시한다. HTTP에서 빈 문장만 보낸 요청은 오류로 처리한다.
- **문자열 비교:** 문자열 `=` 비교는 대소문자를 구분한다.
- **식별자 대소문자:** 테이블과 열 이름은 스키마에 적힌 대소문자와 정확히 일치해야 한다. SQL 키워드는 대소문자를 구분하지 않는다.
- **SQL 문자열 따옴표:** 문자열 값 안의 작은따옴표는 두 번 연속으로 써서 표현한다. 예: `'O''Brien'`.
- **SQL 주석:** 첫 구현 범위에서 지원하지 않는다.
- **SQL 문장 경계:** CLI와 HTTP 모두 문자열 밖의 세미콜론 `;`으로 각 SQL 문장을 끝내야 한다. 문자열 안의 세미콜론은 값의 일부다. CLI는 빈 문장을 무시하고 HTTP의 빈 요청은 오류로 처리한다.
- **빈 문자열과 NULL:** 길이가 0인 문자열 `''`은 허용한다. SQL `NULL`은 지원하지 않으며 값으로 입력하면 오류로 처리한다.
- **INSERT 필수 열:** 자동 부여되는 ID를 제외한 모든 열에 값을 지정해야 한다. 빠진 열이 있으면 오류로 처리한다.
- **자동 ID 입력:** DBMS가 Phase 1부터 삽입 시 ID를 자동 부여하며, 사용자가 `INSERT`에서 ID를 직접 지정하면 오류로 처리한다. ID 발급과 중복 방지를 DBMS가 담당한다.
- **SQL 파일 실행 오류:** 문장을 순서대로 실행하고 오류가 나면 해당 문장에서 중단한다. 앞서 성공한 문장은 유지하고 이후 문장은 실행하지 않는다. 파일 쓰기 오류는 알리며, 테이블과 인덱스의 일관성을 확인할 수 없으면 해당 테이블을 차단한다.
- **SQL 기본 범위:** 단일 테이블에 `INSERT`, 전체 열의 `SELECT`, 열 하나에 대한 `=` 조건 조회를 지원한다. ID 인덱스 조회와 다른 필드의 선형 조회를 표현하기 위한 범위다. 세부 문법과 값의 제약은 미결이다.
- **JOIN은 이번 범위에서 제외한다.** 여러 테이블의 관계를 SQL로 조회하는 기능은 구현과 검증 범위가 넓어지므로 이번 과제에서는 다루지 않는다.

### 스키마와 저장

- **테이블 저장 형식:** 길이 정보를 포함하는 바이너리 형식을 사용한다. 가변 길이 문자열과 레코드 경계를 다루고 레코드 위치를 인덱스와 연결하기 위함이다. 상세 형식은 미결이다.
- **데이터 디렉터리 독점 사용:** 하나의 데이터 디렉터리는 한 DBMS 프로세스만 사용한다. 이미 사용 중이면 나중에 시작한 프로세스는 오류를 반환한다. 구체적인 확인 방법은 미결이다.
- **새 스키마 반영:** 실행 중 추가된 테이블 스키마는 DBMS를 재시작한 뒤 사용할 수 있다.
- **저장 데이터 유지:** 정상 종료 후 재시작해도 성공적으로 저장된 행을 조회할 수 있어야 한다. 비정상 종료 및 전원 장애 후 복구는 지원 범위에서 제외한다.
- **트랜잭션 범위:** 명시적 다중 문장 트랜잭션(`BEGIN`·`COMMIT`·`ROLLBACK`)은 선택 확장 기능이다. 별도 트랜잭션 명령 없이 문장별로 실행하며, 비정상 종료나 쓰기 실패 시 트랜잭션 원자성·복구는 보장하지 않는다.
- **실행 중 스키마 변경:** DBMS 실행 중에는 스키마 파일 변경을 반영하지 않는다. 기존 데이터가 있는 테이블의 스키마는 변경하지 않는다고 가정한다. 변경 여부 감지와 데이터 변환은 지원하지 않는다.
- **잘못된 스키마:** 중복 열이나 지원하지 않는 자료형 등 잘못된 스키마를 가진 테이블은 사용할 수 없게 하고 원인을 오류로 알린다. 오류가 있는 테이블만 차단하고 정상 스키마의 다른 테이블은 사용할 수 있다. 검증 시점은 미결이다.
- **테이블 사전 준비:** 스키마와 테이블은 미리 존재하며 빈 테이블도 빈 데이터 파일을 사전에 준비한다. 데이터 파일이 없으면 자동 생성하지 않고 해당 테이블을 오류 처리한다. SQL로 테이블이나 스키마를 생성하지 않는다.
- **지원 자료형:** 정수와 문자열을 지원한다. 정수 범위와 문자열 길이는 각각의 결정 사항에 따른다.
- **테이블 사용 범위:** 프로그램을 재시작하지 않고 여러 테이블을 사용할 수 있다. 각 SQL 문장은 테이블 하나를 대상으로 하며, `WHERE`는 해당 테이블의 행을 걸러낸다.
- **스키마 제공:** 테이블의 열과 자료형 등의 스키마 정보를 프로그램 코드가 아닌 별도 파일로 제공한다. 파일 형식과 그 밖의 제약 조건은 미결이다.

### 인덱스와 성능

- **성능 비교 완료 기준:** 결과 정확성과 인덱스 사용 여부를 확인하고, 명시된 조건에서 여러 번 조회해 측정한다. 삽입·인덱스 구축·조회 시간을 구분하며 고정 속도 배수를 요구하지 않는다. 기대와 다른 결과의 조건과 원인을 분석한다. 삽입 결과 출력과 조회 결과 전송을 측정에 포함하는지 명시한다. 첫 조회와 반복 조회를 구분하고 조회 순서를 기록한다. 운영체제 파일 캐시를 직접 구현하거나 강제로 비우지 않으며 첫 조회가 반드시 디스크에서 읽힌다고 단정하지 않는다. 100만 건 이상의 인덱스 구축 전후 메모리 사용량과 측정 방법을 기록한다.
- **인덱스 사용 검증:** 테스트에서 조회가 인덱스와 선형 탐색 중 어떤 방식을 사용했는지 확인할 수 있어야 한다. 확인 방법은 미결이다.
- **성능 측정 기록:** 데이터 건수·분포, 조회 조건과 결과 행 수, 반복 횟수, 측정 구간, 실행 환경을 기록하고 삽입·인덱스 구축·조회 시간을 구분한다.
- **조회 순서:** `ORDER BY`를 지원하지 않으며 조회 결과 행의 순서를 보장하지 않는다. 결과 비교는 순서와 무관하게 수행한다.
- **대량 데이터 삽입:** 생성한 SQL 파일에 100만 개 이상의 INSERT 문을 담아 CLI의 기존 SQL 처리기로 실행한다.
- **인덱스 결과 검증:** 같은 ID 조건의 인덱스 조회와 선형 조회 결과가 일치하는지 확인하고 성능 측정 조건과 시간을 기록한다.
- **성능 비교 보강:** 과제의 ID 인덱스 조회와 다른 필드 선형 조회 비교 외에, 같은 ID 조건에서 인덱스 사용과 선형 탐색도 비교한다.
- **필수 ID 열:** 모든 테이블 스키마에는 정수형 `id` 열이 있어야 하며 DBMS가 자동 부여한다.
- **인덱스 갱신 실패:** 파일에 행을 기록한 뒤 인덱스 갱신에 실패하면 삽입 성공을 반환하지 않고, 일관성을 확인할 때까지 해당 테이블의 요청을 차단한다. 저장 여부가 불확실할 수 있다. 차단된 테이블의 조회와 삽입에는 테이블 사용 불가 오류를 반환하며 정상 테이블은 계속 사용할 수 있다. 차단 상태는 실행 중 유지한다. 사용자가 파일을 점검하고 필요한 조치를 한 뒤 재시작하면 파일을 읽고 인덱스를 다시 구축한다. 읽기 또는 인덱스 구축이 실패하면 해당 테이블은 계속 차단한다. 재시작만으로 데이터 복구나 정확성 전체가 보장되지는 않는다.
- **인덱스 재구축 시점:** DBMS 시작 시 유효한 테이블의 파일을 읽어 메모리 B+ 트리 인덱스를 미리 구축한다. 테이블별 오류는 해당 테이블을 차단한다. 구축 실패의 세부 처리는 미결이다.
- **재시작 후 ID:** 각 테이블의 기존 ID 최댓값 다음부터 자동 부여한다. 빈 테이블의 첫 ID는 1이다. ID 범위를 소진하면 새 삽입을 거부하고 오류를 반환한다. 자동 ID는 부호 있는 32비트 정수의 양수 범위를 사용한다.
- **ID 유일성 범위:** 자동 ID는 각 테이블 안에서 유일하며, 서로 다른 테이블은 같은 ID를 사용할 수 있다. 다음 ID도 테이블별로 관리한다.

### HTTP와 동시성

- **HTTP 복수 문장:** 한 요청에 SQL 문장이 두 개 이상이면 어느 문장도 실행하지 않고 요청 전체를 거부한다.
- **HTTP 오류 코드:** HTTP 상태 코드와 별도로 기계가 구분할 수 있는 안정적인 오류 코드와 설명을 JSON으로 제공한다. 코드 목록은 미결이다.
- **서버 접속 범위:** 서버는 로컬 접속만 제공한다. 같은 컴퓨터의 별도 클라이언트에서 HTTP API를 검증한다. 다른 컴퓨터에서의 접속은 필수 범위에서 제외하고 과제 해석을 팀 회의에서 확인한다.
- **HTTP 요청 크기:** 요청 본문은 최대 1 MiB이며 초과하면 HTTP 413으로 거부한다. 조회 응답 크기는 이 제한과 별개다.
- **HTTP 오류 응답:** 응답 전 잘못된 요청이나 SQL 문법 오류는 HTTP 400, 서버 내부 파일 접근 실패는 500, 작업 큐 포화는 503과 오류 내용을 반환한다. 조회 결과 전송 중 오류는 본문 오류 객체로 표현한다. 오류 코드와 메시지의 세부 분류는 미결이다.
- **HTTP INSERT 성공 응답:** 삽입 성공 여부와 자동 부여된 ID를 반환한다. 오류 응답은 HTTP 오류 응답 결정에 따른다.
- **조회 중 삽입 대기:** 첫 구현에서는 조회가 끝날 때까지 같은 테이블의 삽입을 기다리게 한다. 순차 응답을 천천히 받는 클라이언트가 삽입을 지연시킬 수 있다. 연결 종료 감지 또는 전송 정체 시간 제한에 따라 SELECT가 중단되면 읽기 잠금을 해제한다. 느린 조회는 제한에 도달하기 전까지 작업자와 정상 종료를 지연시킬 수 있다.
- **HTTP 조회 결과:** 조회 결과를 임의로 잘라내지 않고 순차적으로 전달한다. 전체 결과를 한꺼번에 메모리에 모으지 않아도 되도록 한다. 응답 본문에서 시작·행·완료·오류를 구분한다. 완료 표시가 없거나 오류가 발생한 결과는 불완전한 결과로 판단한다. 한 줄에 JSON 객체 하나씩 전달하며, 각 객체로 시작·행·완료·오류를 나타낸다. 예시는 아래와 같다. 오류 객체의 상세 내용은 미결이다.

  ```json
  {"type":"start"}
  {"type":"row","data":{"id":1,"name":"Ada"}}
  {"type":"done"}
  ```
- **HTTP 요청의 SQL 범위:** HTTP `POST /query` 요청의 JSON 본문 `sql` 필드에 SQL 문장 하나만 허용한다. 응답의 세부 형식은 미결이다.
- **외부 API 프로토콜:** Phase 3 서버는 HTTP API로 제공한다. Phase 1 CLI는 별도로 SQL 파일을 받아 같은 DB 엔진을 사용한다. HTTP 라이브러리와 오류 객체 등 응답 세부 형식은 미결이다.
- **SELECT 전송 정체 제한:** 연결은 유지되지만 응답 데이터 전송이 일정 시간 진전되지 않으면 SELECT를 중단하고 읽기 잠금 등 자원을 정리한다. 전체 조회 시간은 제한하지 않는다. 제한 시간의 기본값은 구현 시 정하고 설정할 수 있게 한다.
- **클라이언트 연결 종료:** 서버가 연결 종료를 감지하면 SELECT를 중단하고 읽기 잠금과 작업자 등 자원을 정리한다. 수락한 INSERT는 연결이 끊겨도 처리를 마치며, 응답을 받지 못한 클라이언트가 재시도하면 중복이 발생할 수 있다. 연결 종료의 즉각적인 감지는 보장하지 않는다.
- **서버 정상 종료:** 종료가 시작되면 새 요청을 받지 않고 수락 전 연결은 닫는다. 이미 수락한 요청은 큐의 대기 요청을 포함해 기존 정책에 따라 처리한 뒤 종료한다. 다만 연결 종료가 감지된 SELECT는 중단하고 자원을 정리한다. 정상 종료 대기에는 시간 제한을 두지 않으며 느린 요청이나 연결로 종료가 오래 걸릴 수 있다.
- **HTTP 요청 수신 정체 제한:** 요청 수신이 일정 시간 진전되지 않으면 연결을 닫고 SQL을 실행하지 않는다. 해당 요청은 수락되지 않은 것으로 취급한다. 구체적인 기본 시간은 구현 시 정한다.
- **HTTP 요청 수락 시점:** 완전한 HTTP 요청을 읽고 기본 검증을 마친 뒤 작업 큐에 넣은 시점을 수락으로 본다. 수락 전 연결이 끊기거나 요청이 잘못된 경우, 큐가 가득 차 거부된 경우에는 SQL을 실행하지 않는다. 큐에 들어간 INSERT는 연결 종료 후에도 처리한다. 큐에 넣기 전 기본 검증은 HTTP 요청·본문 크기·JSON 및 SQL 필드 확인을 포함한다. SQL 문장 수와 문법 검사는 작업자가 처리하며, 실패하면 어떤 문장도 실행하지 않고 오류를 반환한다.
- **작업 큐 용량 초과:** 작업 큐가 가득 차면 새 요청을 추가하지 않고 서버가 바쁘다는 오류를 반환한다. 작업자 수, 큐 크기와 오류 응답 형식은 미결이다.
- **같은 테이블의 동시 요청:** 같은 테이블의 삽입은 해당 테이블의 다른 삽입 및 조회와 겹치지 않도록 조정한다. 삽입 중이 아니고 대기 중인 삽입도 없을 때는 같은 테이블의 조회 여러 개를 동시에 허용한다. 삽입이 대기하기 시작하면 새 조회는 기다리며, 이미 실행 중인 조회가 끝나면 대기 중인 삽입을 처리한다. 다수 대기 요청의 엄격한 순서와 최대 대기 시간은 보장하지 않으므로 삽입이 계속되면 조회가 오래 기다릴 수 있다. 구체적인 동기화 방식은 미결이다.
- **서로 다른 테이블의 동시 요청:** 서로 다른 테이블을 대상으로 하는 요청은 동시에 처리할 수 있어야 한다. 작업 큐 등 공통으로 사용하는 상태의 동기화는 별도로 설계한다.
- **응답 없는 INSERT 재시도:** 자동 중복 제거는 필수 범위에서 제외한다. 응답을 받지 못하면 삽입 결과가 불확실하며, 확인 없이 재시도하면 중복 행이 생길 수 있다.

## 완료 기준 초안

### Phase 1

- 사전에 준비된 스키마와 테이블에 CLI로 SQL 파일을 실행해 행을 삽입하고 조회할 수 있다. 여러 테이블을 한 프로세스에서 각각 사용할 수 있다.
- Phase 1에서 테이블별로 ID를 자동 부여하고 직접 입력을 거부한다. 정상 종료 후 재시작해도 기존 ID와 중복되지 않게 다음 ID를 부여한다.
- SQL 문법, 자료형, 필수 열 등 잘못된 입력을 오류로 구분한다. SQL 파일의 오류 이전에 성공한 문장은 유지하고 이후 문장은 실행하지 않는다.
- 성공적으로 삽입한 행은 정상 종료 후 재시작해도 조회할 수 있다. 파일 입출력 오류는 알리고 일관성이 불확실하면 해당 테이블을 차단한다.

### Phase 2

- 각 테이블의 자동 ID는 테이블 내에서 유일하며 재시작 후 기존 최댓값 다음으로 발급된다. 재시작 시 파일에서 메모리 인덱스를 구축한다.
- 100만 개 이상의 INSERT를 SQL 처리기로 실행한다. ID 인덱스 조회와 다른 필드의 선형 조회를 측정하고, 같은 ID 조건의 인덱스·선형 조회 결과와 시간도 비교한다. 측정 환경과 구간을 기록한다.
- 테스트에서 ID 조회가 실제 인덱스를 사용했는지, 다른 필드 조회가 선형 탐색을 사용했는지 확인한다.

### Phase 3

- 외부 클라이언트는 HTTP로 SQL 한 문장을 실행하고 결과나 오류를 확인할 수 있다. 같은 컴퓨터의 별도 클라이언트에서 로컬 HTTP API를 검증한다.
- 스레드 풀에서 다른 테이블 요청은 동시에 처리할 수 있다. 같은 테이블의 조회끼리는 함께 실행할 수 있고 삽입은 같은 테이블의 조회·삽입과 겹치지 않는다. 삽입이 대기 중이면 새 조회가 먼저 시작하지 않는다.
- 큐가 가득 차면 새 요청에 오류를 반환하고, 정상 종료 시 이미 수락한 요청을 처리하되 연결 종료가 감지된 SELECT는 중단한다. 조회 결과는 순차 전송하며 완료 표시 없는 결과를 불완전하게 판단한다.

## 주요 검증 시나리오 초안

### SQL과 파일 저장

- 빈 SQL 파일은 성공 종료한다. 여러 문장을 순서대로 실행하고, 중간 오류 시 이전 성공은 유지하며 이후 문장은 실행하지 않는다.
- macOS와 WSL 2 사이에서 테이블 데이터 파일을 복사해 읽고 삽입·조회 결과를 확인한다.
- 빈 테이블과 여러 사전 준비된 테이블에서 INSERT와 SELECT를 실행한다. 테이블이나 데이터 파일이 없으면 새로 만들지 않고 오류를 알린다.
- 정수·UTF-8 문자열·빈 문자열·작은따옴표 이스케이프를 읽고 쓴다. INSERT 열 순서가 스키마와 달라도 값이 해당 열에 연결된다.
- 열 목록이 없거나 하나의 VALUES 절에 여러 행이 포함된 INSERT를 거부한다. 32비트 정수의 최솟값과 최댓값을 허용하고 범위 초과는 거부한다. 중복되거나 없는 열, 누락된 필수 열, 열·값 개수 불일치, 자료형 불일치, 잘못된 UTF-8, 문자열 값의 널 바이트, 닫히지 않은 문자열, 세미콜론 누락도 거부한다.
- 정상 조회 0행과 실행 오류를 구별한다. 성공적으로 저장한 행은 정상 종료 및 재시작 후에도 조회된다.
- 파일 입출력 오류를 알리고 잘못된 데이터를 정상 행으로 취급하지 않는지 확인한다. 비정상 종료 후 복구와 부분 쓰기의 원자성은 보장 범위에서 제외한다.

### 인덱스와 성능

- B+ 트리 검색, 존재하지 않는 ID, 리프 및 내부 노드 분할, 루트 분할을 검증한다. 기존 키와 레코드 위치가 분할 후에도 유지돼야 한다.
- 삽입과 재시작 이후 인덱스 조회와 선형 조회의 결과를 대조하고 실제 조회 방식을 확인한다. 테이블별 ID의 독립성과 재시작 후 다음 ID 결정이 올바른지 검증한다.
- 인덱스 갱신 실패 시 성공을 반환하지 않고 일관성을 확인할 때까지 해당 테이블을 차단하는지 확인한다.
- SQL 처리기로 100만 건 이상을 삽입하고 ID 인덱스·다른 필드 선형 조회 및 같은 ID 조건의 인덱스·선형 조회를 반복 측정한다. 기본 비교는 같은 한 행을 반환하는 고유 이름과 ID를 사용하고, 존재하지 않는 값과 앞·중간·뒤 위치도 조회한다. 정확성, 데이터 분포, 조회 결과 수, 환경과 측정 구간을 함께 기록한다.

### HTTP와 동시성

- 별도 로컬 클라이언트로 INSERT와 SELECT, 0행 결과, 잘못된 요청, 오류 응답 및 부여된 ID를 확인한다. 요청 수신이 제한 시간 동안 진전되지 않으면 SQL을 실행하지 않는지도 확인한다. 복수 SQL 문장은 어느 것도 실행하지 않고 거부한다.
- 큰 조회 결과를 순차 전송하고, 전송 도중 오류나 연결 종료로 완료 표시가 빠진 결과를 불완전하게 구분한다. 전송이 제한 시간 동안 진전되지 않으면 SELECT가 중단되고 자원이 해제되는지 확인한다.
- 같은 테이블에서 동시 삽입과 조회·삽입을 겹쳐 ID 및 파일·인덱스 일관성을 확인한다. 조회끼리와 서로 다른 테이블 요청은 동시에 처리 가능한지 확인한다. 삽입이 대기 중일 때 새 조회가 먼저 시작하지 않는지도 확인한다.
- 큐가 가득 찬 경우 요청을 거부한다. 정상 종료 중에는 새 요청을 받지 않고 수락 전 연결을 닫으며 수락한 요청을 처리한다. 연결 종료가 감지되면 SELECT는 중단하고 자원을 정리하며, 수락한 INSERT는 처리를 마친다.
- 동일 데이터 디렉터리에 두 번째 DBMS 프로세스를 시작하면 오류로 거부한다.

## 범위 밖 및 한계

- 인증과 권한 관리는 구현하지 않고 신뢰할 수 있는 로컬 실습 환경에서 사용한다. 로컬 바인딩만으로 같은 컴퓨터의 다른 사용자나 프로그램을 인증할 수 없다. 데이터 파일 권한은 실행 환경에서 확인한다.
- 기존 데이터가 있는 테이블의 스키마는 변경하지 않는다고 가정하며, 변경 감지와 자동 변환은 지원하지 않는다.

- 체크섬 기반 손상 감지, 손상 파일 자동 복구, 비정상 종료 또는 전원 장애 후 복구, 중단된 삽입의 원자성 보장은 지원하지 않는다.
- 파일·인덱스 갱신 중 오류가 발생하면 INSERT 결과가 불확실할 수 있다.

## 팀 회의에서 확인할 사항

이 문서는 개인안이며 아래를 포함한 설계 결정은 아직 팀 합의가 아니다.

- **과제 해석:** 외부 클라이언트가 다른 컴퓨터에서도 접속할 수 있어야 하는가? 개인안은 로컬의 별도 클라이언트만 필수로 검증한다.
- **개발 환경:** Windows 팀원 모두 WSL 2를 사용할 수 있는가? 개인안은 macOS 네이티브와 Windows의 WSL 2를 지원한다.
- **범위와 우선순위:** 단일 테이블 SQL, 별도 스키마 파일, 자동 ID, 파일 기반 저장, 100만 건 비교와 HTTP 스레드 풀을 팀안의 기본 범위로 삼을지 다른 개인안과 비교한다. JOIN, 명시적 트랜잭션 및 비정상 종료 후 복구는 개인안의 필수 범위 밖이다.
- **운영 정책:** 순차 조회 중 같은 테이블 삽입 대기, 삽입 우선, 정체 시간 제한, 로컬 인증 미지원과 정상 종료 무기한 대기를 팀이 수용할지 검토한다.

## 구현 설계에서 정할 사항

- 두 지원 환경에서 동일하게 해석할 바이너리 레코드와 스키마 파일의 상세 형식, 테이블 파일의 구체적인 점검 방법.
- 인덱스 구축 중 메모리 할당 실패를 알리는 구체적인 오류 코드.
- HTTP 요청 수신 및 SELECT 전송 정체 제한의 기본값과 설정 방법. 정상 종료를 무기한 기다리는 개인안은 유지한다.
- B+ 트리 노드 크기, 인덱스 사용 여부를 검증하는 방법과 같은 ID 조건의 선형 탐색을 강제하는 검증·측정용 경로.
- HTTP 라이브러리, 오류 코드 목록, 순차 응답 중 오류 형식과 느린 연결 처리.
- CLI 출력 서식과 성능 실험의 데이터 분포·반복 횟수.
- 작업자 수와 작업 큐 크기.
- 데이터 디렉터리의 프로세스 간 독점 사용을 확인하는 방법.
