# 002 커서 부분 크기

## 앞 기록과 달라진 점

커서(티켓 13)의 첫 기록입니다. 001은 엔진 함수를 직접 재고, 이 기록은 HTTP 서버를 거친 클라이언트 쪽 시간을 잽니다.

## 결론

- **상한 1만을 유지합니다.** 1만 건 한 부분의 응답은 중앙값 39\~42 ms, 응답 538,022바이트이고, 서버의 최대 RSS는 기준보다 10.3 MiB 늡니다.
- **10만 건은 메모리 비용이 큽니다.** 한 부분의 응답이 중앙값 326\~401 ms이고, 최대 RSS가 기준보다 319.6 MiB 늡니다. 작업 스레드 8개가 동시에 이런 부분을 만들면 이 머신의 메모리(15 GiB)에서 수 GiB가 됩니다. 전체 100만 건을 받는 시간은 3.95 s로 1만(5.65 s)보다 짧을 뿐입니다.
- **1천 건은 메모리 이득이 작습니다.** 한 부분이 4\~5 ms, RSS 증가가 2.1 MiB이지만, 요청이 100배 많아져 전체 시간은 1만과 비슷합니다(5.31 s 대 5.65 s).
- **뒤 부분도 앞 부분과 같은 시간입니다.** 1만 건 부분 100개의 중앙값(41.9 ms)이 첫 부분(38.9 ms)과 비슷합니다. 커서 위치에서 바로 읽기 시작하므로 뒤 부분이 앞 record를 다시 읽지 않습니다.
- 모든 크기에서 받은 record의 id가 1부터 1,000,000까지 빠짐과 중복 없이 이어졌습니다.

## 방법

`scripts/bench-cursor.py`가 `generate-users.py`와 같은 모양의 record 100만 개(62,000,000바이트)를 테이블 파일에 바로 씁니다. 부분 크기마다 서버를 두 번 띄웁니다.

1. 기준: `WHERE id = 1` 하나만 보내고 서버를 끕니다. 서버가 끝난 뒤 `wait4`가 돌려준 최대 RSS가 기준 RSS입니다. 테이블을 읽고 B+ 트리를 만든 메모리가 들어 있습니다.
2. 측정: `SELECT * FROM users;`의 첫 부분을 20번 받아 시간을 잽니다. 그다음 `next_cursor`가 없을 때까지 같은 SQL을 커서와 함께 보내 전체를 받고, 부분마다 시간을 잽니다. 서버를 끈 뒤 최대 RSS를 읽습니다.

시간은 클라이언트(Python `http.client`)가 요청을 보내고 응답 본문을 다 읽기까지입니다. JSON 해석 시간은 넣지 않습니다. 요청은 하나씩 보냅니다.
